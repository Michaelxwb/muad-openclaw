# MSSP 事件深度分析与推送内容

根据事件 ID 与 CGID 查询终端 GPT 模型日志库。一个 CGID 命中一条或多条记录时，只保存 `seq` 最大的最新一条 GPTRawLog；随后立即解析为分析子文件，并仅基于这些子文件、事件上下文和人工处置状态完成推送判定与原有客户推送文案。完整 GPTRawLog 只作原始证据归档，后续研判不得直接读取。

## 用法

```bash
python3 scripts/run.py --event-id E26090304170 --cgid 17937119307574291111
python3 scripts/run.py --event-id E26090304170 --cgid 17937119307574291111 \
  --event-context-json '{"company":"客户全名","event_name":"事件名","host_ip":"10.0.0.1"}'
```

同一对话内，用户在 `monitor-mssp-events` 结果后说“推送第 N 个事件”或点名事件时，自动把该条监控结果中的事件 ID、客户、事件名、主机、资产、IOC、关联告警和处置状态组装为 `--event-context-json`；不得要求用户重复输入。若该事件没有 CGID，只询问 CGID。脱离监控结果单独调用时，允许用户手动提供事件 ID、CGID 和缺失上下文。

独立调用且没有上游事件上下文时，`run.py` 会用原 `monitor-mssp-events` 的 `event_detail` 请求和资产请求补齐信息；其 URL、请求方法、请求头、Cookie/CSRF、timezone、请求体、超时和重试逻辑保持不变。登录态仍由 `session-manager` 获取，Skill 名使用当前独立 Skill 的 `mssp-event-push-content`。

## 最终聊天输出硬约束

当最终推送文案已经生成时，面向用户的最终回复只能包含两类内容：**本次恶意 IOC 对应的 TI 摘要截图**和**一个无语言标记的 Markdown 文案代码块**。二者必须在同一轮回复中一起输出：

````markdown
MEDIA:<归档后的TI摘要截图绝对路径1>
MEDIA:<归档后的TI摘要截图绝对路径2>
```
{最终推送文案全文}
```
````

- 每个需要截图的恶意 IOC 输出一行 `MEDIA:<归档后的摘要截图绝对路径>`；只输出裁剪后的摘要图，不输出原始整页截图。
- 所有 TI 摘要截图必须先成功归档，再使用归档脚本返回的 `summary_screenshot` 路径输出；不得引用临时 browser 截图路径。
- 除 `MEDIA:` 图片行和文案代码块外，不得出现任何字符、标题、解释、摘要、判定说明或收尾语。
- 禁止输出“已生成”“已完成”“推送文案如下”“事件文件夹”“判定”“待确认项”“已附 N 张截图”等过程或结果说明。
- 禁止输出 TI 字段摘要、证据 Markdown、普通文件链接或事件归档信息；截图只通过上述 `MEDIA:` 行展示。
- 禁止向用户展示内部思考、分析过程、工具调用摘要或中间产物内容。非缺少必填输入、需要人工补充处置状态或执行失败的场景，不得发送过程性回复。
- 若判定为“不推送”或没有符合截图门禁的恶意 IOC，则不输出 `MEDIA:`，只输出一个代码块，代码块内放置最终面向用户的结论或约定文案，不再附加解释。
- 只有在尚未形成最终文案且确实缺少必填输入、需要人工补充处置状态或执行失败时，才允许在最终交付规则之外提出必要问题或错误信息；一旦形成最终文案，立即恢复上述“TI 摘要截图 + 唯一文案代码块”规则。

- `ti-redirect-analyze` — 独立 Skill；推送判定为“推送”且解析结果中存在已确认恶意 IOC 时调用以生成 TI 截图证据。

## 用户指定 Webhook 推送（可选能力）

当用户在本轮对话中**明确给出了 webhook 地址**（企微群机器人 webhook，形如 `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=<KEY>`），除正常产出推送材料外，还必须启用「完成一个事件就推送一个到该 webhook」的实时推送；用户未指定 webhook 时不启用本能力，行为与本 skill 原有流程一致。

### 触发与范围

- 触发条件：用户本轮消息里出现了明确的 webhook URL（含 `key=` 的企微机器人地址）；或用户直接给出 webhook key（形如 32 位串或带连字符的 UUID，如 `7345e237-1507-4d53-87cf-7392576e6e17`），由执行方拼到固定前缀 `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=*** 之后。
- 适用对象：本轮处理的**每一个事件**（逐事件、非批量合并），处理完一个立即推送一个。
- 顺序：每个事件先完成 §2–§6 的全部流程（查询解析 → 推送判定 → 情报/全网排查 → TI 截图 → 文案），再把该事件的结果推送到 webhook，随后再处理下一个事件。
- 判定“不推送”的事件同样要推送一条（结果 = 不推送结论 + 依据），不得静默跳过。
- **发送纪律（强制）**：一个事件的文案必须**在该事件全部材料生成完毕后整条一次发送**（超长时由 `send_webhook.py` 自动按 4096 字节硬截断为多条，非循环拆段）。**严禁**发送测试消息、占位消息或任何非该事件最终结论的内容；**严禁**在脚本之外自行拆段并发。

### 推送内容与格式（按当前验证通过的格式，不得改写）

每个事件推送到 webhook 时，**依次发送两条消息**：先文字、后图片（该事件有 TI 摘要截图时才发图片；判定“不推送”或无符合条件的恶意 IOC 时只发文字）。

**1）文字消息（`msgtype=markdown`）**：正文 = 该事件的最终结果。判定“推送”时，直接放该事件定稿的 `*_推送文案.md` 全文；判定“不推送”时，放“不推送”结论与判定依据。请求体：

```json
{
  "msgtype": "markdown",
  "markdown": { "content": "<该事件结果正文>" }
}
```

**2）图片消息（`msgtype=image`，直接用 base64，不走 upload_media）**：逐个 TI 摘要截图发送，`base64` 为该摘要 PNG 的 base64 编码，`md5` 为该图片内容的 md5（32 位小写十六进制）。请求体：

```json
{
  "msgtype": "image",
  "image": { "base64": "<图片base64>", "md5": "<图片md5>" }
}
```

- **图片必须走上面这个 base64 直发格式**：企微群机器人 webhook 的 `upload_media` 接口不支持 `type=image`，无法拿到可供 `image` 消息使用的 `media_id`；直接 POST `image.base64`+`image.md5` 是唯一可用的内嵌图片发送方式（实测 `errcode:0`）。
- base64 取**归档后的 TI 摘要截图**（`*_情报截图证据.md` 记录的 `summary_screenshot` 路径文件），不要用原始整页截图，也不要用临时 browser 截图路径。
- 多个恶意 IOC 时，逐张依次发送多条 `image` 消息。

### 发送实现（统一由 `scripts/send_webhook.py` 执行，best-effort，失败不阻断主流程）

**必须用本 skill 自带的 `scripts/send_webhook.py` 发送，不要另行手写 `curl` 或拼 JSON**，以保证文字/图片两种消息体与本规范完全一致（该脚本就是上文两段请求体的实现）。

```bash
# 1) 文字消息（markdown）：正文 = 该事件定稿的 *_推送文案.md（判定“不推送”时传结论文本/文件）
python3 scripts/send_webhook.py --url "<webhook URL>" --text-file "<事件文件夹>/xxxx_推送文案.md"
#   或直接传文本：python3 scripts/send_webhook.py --url "<webhook URL>" --text "<正文>"

# 2) 图片消息（base64 直发）：对每个 TI 摘要截图各调一次">
python3 scripts/send_webhook.py --url "<webhook URL>" --image "<事件文件夹>/TI_xxx_摘要.png"
```

- 脚本行为：文字→`{"msgtype":"markdown","markdown":{"content":正文}}`；图片→`{"msgtype":"image","image":{"base64":<图片base64>,"md5":<图片内容md5>}}`。每条消息一次 HTTP POST（`Content-Type: application/json`），`errcode==0` 视为成功，结果以 JSON 打到 stdout。
- **文字超长按 4096 字节硬截断（自动）**：企微 markdown 单条 `content` 上限为 **4096 字节（UTF-8，非字符数）**。`send_webhook.py` 会在超过上限时**从开头顺序累积、满 4096 字节即断一条**，剩余继续切，直到发完；**不在段落边界对齐、不做对半均衡、不自加 `(i/N)` 之类前缀**（正文保持原文）。分段数量就是内容字节数 ÷ 4096 向上取整（如 4932 字节 → 2 条，约 4094 + 838 字节）。**禁止在脚本之外另行拆段循环发送**。
- **URL 编码**：webhook 地址可能含非 ASCII 字符（如 `…`），`send_webhook.py` 会自动做百分号编码，不因此报 `ascii codec` 错误。
- **webhook key 处理**：用户可直接提供 key（如 `7345e237-1507-4d53-87cf-7392576e6e17`），执行方自行拼到固定前缀 `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=*** 之后，**key 原样使用，不做去连字符等改写**。
- **严禁发送测试/占位/过程性消息**：通过 `send_webhook.py` 发送的正文**只能是该事件最终定稿的结果**（推送文案全文，或“不推送”结论与依据）。**严禁**发送测试消息（如“测试中文消息”）、占位消息（如“生成中/稍后送达”）、进度说明、连通性验证等任何非最终结论内容。若发送失败，只如实记录错误，**不得自行补发任何过程性消息或测试消息**，也不得改为拆段刷屏。
- **职责边界**：`run.py` 只负责“查最新 GPTRawLog → 保存原始日志 → 解析子文件”，**不参与 webhook 推送**；一切送达动作均在流程最后一步由 `send_webhook.py` 完成。
- 发送属于「送达动作」，任何一条失败（网络/校验/接口错误）都只在本轮结果里如实记录该条未送达（脚本以 `errcode:-1`/实际 errcode 返回），**不得**因此中断后续事件的推送或篡改推送文案内容。
- 不得把 webhook key 或用户原始地址写入事件归档、推送文案或任何落盘文件；webhook 地址只作命令行参数传入，仅用于本次发送。
- 严禁改动、润色或重排要推送的**文字内容**：文字就是该事件定稿的 `*_推送文案.md`（或“不推送”结论）原文，图片就是归档摘要图原文；`--text-file` 直接传文件路径，不手工改写正文。

### 与最终聊天输出的关系

webhook 推送与 §最终聊天输出硬约束并行，互不覆盖：聊天回复仍遵守「TI 摘要截图 `MEDIA:` 行 + 唯一文案代码块」的合同；webhook 推送是该合同之外的、用户额外指定的实时送达通道。

## 流程

### 1. 输入检查

确认核心输入是否就绪：

- **事件 ID**（必须）：优先来自用户刚选中的监控结果，亦可手动输入。
- **CGID**（必须）：当前由用户人工提供；缺失时只询问此项并暂停。
- **事件与资产上下文**：优先自动承接监控结果；**其中的数字 `company_id` 为 §4.2 全网排查必需**（`telemetry-entity-hunt --company-id`），承接不到时须向用户索取，不得臆造。独立调用时允许补充其余字段，缺失字段统一用 `-`。

### 2. 查询最新 GPTRawLog 并解析

```bash
python3 scripts/run.py --event-id <事件ID> --cgid <CGID> [--event-context-json '<监控事件JSON>']
```

`run.py` 调用原 ClickHouse 查询脚本，按 CGID 查询并保存 `seq` 最大的最新一条，再调用解析脚本。查询命中多条时不得合并多条 RawLog，也不得把旧记录送入分析。

产出 `事件归档/{客户}_{时间戳}_{主机IP}_{事件名}/` 事件文件夹（统一归档根自动解析，见 resolve_archive_root），内含：

1. `*_分析输入.md` — 供后续分析的结构化摘要：事件名称、GPT研判标签、定性标签、analyseAnswer 全文、gptResponse 结构化研判（analysis 的 title/explain/evidence）、威胁情报 IOC 汇总、恶意实体（根因/入口）、终端GPT处置建议、进程树概览
2. `*_gptInput.json` — 完整 threatList / treeList / virtualEdges（行为数据原始输入）
3. `*_基础信息.json` — cgId / alertId / agentId 等

**重点关注字段：**

- `analysePrompt` 中的 `threatList`（情报命中）、`treeList`（进程行为树）、`virtualEdges`（跨树行为关系）——三者构成完整行为输入
- `analyseAnswer`：标签（black/gray/white）、攻击过程分析、定性标签、事件总结、入口信息（入口名/动作/根因实体）、处置建议
- `taskContent.gptResponse`：结构化研判 analysis、恶意实体（hashTi/ipTi）、disposeSuggestion

从这一步起，后续 Agent 只能读取 `*_分析输入.md`、`*_gptInput.json`、`*_基础信息.json`、`事件上下文.json` 和 `事件与资产信息.md`。不得为了研判再打开、粘贴或通读完整 GPTRawLog；原始文件仅供留档追证。

### 3. 推送判定

**先做判定**——本节决定是否继续走后续流程；判定「不推送」则流程到此为止（不补情报、不全网排查、不截图、不生成文案）。

**不推送的场景（命中即停，输出不推送说明）：**

- 业务：资产/事件属于业务行为（如企业合规预装、测试验证），写明业务名与依据
- 低危：gray 标签、低危 PUP/广告软件、无完整攻击链的可疑行为，**即使命中情报也不用推送**，以下场景不用推送
  - **PUP / 广告 / 捆绑软件类告警** —— 有有效厂商数字签名的灰色软件（万能五笔、2345安全卫士、鲁大师、Win解压缩、zip万能压缩、AnyWhere 等）的正常更新、插件加载行为。
  - **正版软件 P2P / CDN 外联及系统网络行为命中威胁情报** —— 迅雷、QQ音乐、百度网盘、Motrix 等 P2P 下载/流媒体的正常外联，共享节点 IP 被情报标黑；
  - **签名商业软件的正常注入** —— 飞书、豆包、Arc 浏览器、搜狗输入法、QoderWork、DataCloak 等正常跨进程机制触发注入/进程间调用/Parent PID Spoofing类行为规则
  - **合法工具、厂商正规软件及测试场景行为** —— 如亚信入网小助手的正常安装（Add-MpPreference 加 Defender排除）、终端工具自带注入（WindTerm/clink）、厂商入网规范管理软件（infogo）
- 误报/无威胁：white 标签，敏感行为有合理解释；未建立连接且无关联事件的单次恶意域名访问

**推送的场景（全部满足）：**

- black 标签，且存在真实攻击特征之一：恶意文件落地并执行（情报判定恶意程序）、木马/远控/间谍行为（C2外联、持久化、注入等）、攻击链完整（投递→执行→持久化→C2）

输出 `*_推送判定.md`：

```markdown
# 推送判定
- 事件：{事件名称} | 主机：{IP}（{资产名}） | 标签：{black/gray/white}
- 判定：推送 / 不推送（原因：业务 / 低价值 / 误报 / 无真实攻击）
- 判定依据：逐条列出（情报命中、攻击链、业务归属等）
- GPTRawLog 解析结果中的恶意实体与行为证据摘要
- 下一步：{生成推送文案 / 归档观察 / 无需动作}
```

### 4. 调用情报接口补充情报与全网排查

**触发条件**：仅当 §3 判定为「推送」时执行本节；判定「不推送」直接跳过（不补情报、不全网排查、不截图）。

#### 4.1 调用情报接口补充情报

**仅针对解析结果 `threatList` 中命中情报的实体**调用情报接口`ioc-context`；行为树中出现但未命中情报的其他实体（事件其他实体段）默认不调用。如需调查，用户可手动指定任意实体（`--ioc` 参数）。

- `ioc-context`：输入 IOC，返回研判上下文（【研判结论】【研判依据】【影响评估】）

#### 4.2 调用 telemetry-entity-hunt 全网排查

补充完情报后，对**事件研判后最需要调查的 IOC** 调用独立的 `telemetry-entity-hunt` 做全网排查，确认该 IOC 是否已在客户全网扩散（判断“没扩散”的事实依据）。

**入参（三项必给）：**

| 参数 | 取值来源 |
|---|---|
| `<实体值>`（IOC，**仅限 hash / ip / domain**） | 事件研判后**最需要调查**的那个 IOC（如 C2 IP、恶意域名、恶意文件 hash） |
| `--tenant` | `*_基础信息.json` 中的 `tenantId` |
| `--company-id` | `monitor-mssp-events` 的输出（本轮承接的数字 company_id） |

```bash
python3 scripts/hunt_entity.py <IOC> --tenant <tenantId> --company-id <company_id> --asset --mode all
```

- `--asset --company-id` 缺一不可：排查命中的是 agentId，客户不可读，必须翻译成终端资产后再交付。
- 0 命中即“未扩散”结论；有命中须给出命中终端（用资产信息表述）与台数。
- 缺 `company_id` 或调用失败时如实记录，不得臆造排查结论。

**产物**：把调用结果写入事件文件夹的 `*_全网排查.md`，作为推送文案【事件遏制&处置】第二点「全网排查」的材料。

#### 4.3 调用 ti-redirect-analyze 生成 TI 截图

只从解析子文件的 `threatList` 和现有定性中识别已确认恶意的 IOC，作为推送后的 TI 截图候选；仅出现在行为树但没有恶意证据的实体不截图。

- 对候选逐个调用独立的 `ti-redirect-analyze`（输入 IOC，返回 TI 截图证据）。
- 无已确认恶意 IOC 时，不调用 TI Skill。

### 5. 生成推送文案

以 `*_分析输入.md` + `*_gptInput.json` + `*_基础信息.json` + `事件与资产信息.md` + `*_全网排查.md` 为输入，生成推送文案 `*_推送文案.md`。

**推送文案 = 两段**，顺序固定，写在同一个 `*_推送文案.md` 内、对外先后一并发出：

1. **第一段·凝练版**（置顶）——客户一眼抓住要害，句式与硬性要求见 §5.2；
2. **第二段·标准详版**（默认格式不变）——模板见 §5.1，正文分项要求见 §5.3。

### 5.1 第二段·标准详版（模板 + 抬头字段规则）

```
【深信服 安全事件通告】{处置结果句，见下表}
事件名称：{事件名}
事件类型：{事件类型（木马/钓鱼/广告软件/恶意程序/远控等）}
事件ID：{E…}
影响业务：{IP}(主机名称：{主机名}、资产组：{资产组}、资产类型：{资产类型}、MAC地址：{MAC}、账号：{账号})
资产信息：{资产类型+资产名（含用户 人名/账号，如 个人PC Ren（用户 刘仁杰））}
告警来源：{NGES 或实际来源}
组件检出时间：{首次发现，YYYY-MM-DD HH:MM:SS}
业务危害：{一句业务可读的消解句，如“木马已被 NGES 实时拦截，未对您的系统造成实际危害”}

【事件概述】{编号列表：每条=时间点+该时刻关键动作；收束为当前处置/危害状态}

【事件研判】{先定性一句 + 证据链：静态特征分析（签名滥用/白加黑/随机路径/伪装名）→ 动态行为（计划任务持久化/加白/删卷影/禁更新/外联C2等，逐条给实体与指令）；末尾单列一段如实、结合业务的危害陈述}

【事件遏制&处置】
深信服MSS已完成：
{1. 威胁实体遏制：[已遏制] C2/IOC/恶意域名封堵+黑名单/情报监测同步，可联动识别同源变种}
{2. 全网排查：[已处置] 对 §4.2 选定 IOC 的全网排查结论**做一句话总结**（材料取自 `*_全网排查.md`）：如“已对全网排查，未发现其他主机命中”或“已对全网排查，发现 N 台主机命中，均已处置”}
需要老师处置内容：
{1. 仅客户必须动手的最小项 [待处置]，≤2~3 条}
```

**抬头字段规则**（置顶必带，结果前置，字段值取平台事件/告警/事件名与事件类型、事件ID、检出时间及前置资产业务信息，缺值用 `-`，不得臆造）：

| 字段 | 规则 |
|---|---|
| 标题 | `【深信服 安全事件通告】{处置结果句}`；已彻底拦住 → `已遏制，未对系统造成实际危害`；已按住但留有残留待客户动手 → `已遏制，存在残留待处置`；仍活跃未按住 → **不得写“已遏制”**，如实写状态（如“检出并在处置中，请尽快配合”） |
| 影响业务 | 必须按 `{IP}(主机名称：{主机名}、资产组：{资产组}、资产类型：{资产类型}、MAC地址：{MAC}、账号：{账号})` 拼接（五要素均来自 事件与资产信息） |
| 告警来源 | 取事件数据源；来源为 NGES 时固定写 `NGES`，其余按实际来源写 |
| 业务危害 | 一句业务可读的话简洁说清现状/消解结论，不堆技术细节 |
| 组件检出时间 | 首次发现时间，`YYYY-MM-DD HH:MM:SS` |

**阅读排序**：结果（事情大不大/是否已拦）→ 要不要动 → 发生了什么。严重程度词（高危/中危/低危）按事件定性/情报等级如实标，未定级不准臆造；**严重程度只标在第一段凝练版首词**（见 §5.2），抬头标题只承载处置结果句。

### 5.2 第一段·凝练版

在标准详版之上先生成**一段高度凝练的推送话术**，让客户一眼看出：攻击是真的、已被按住、没扩散、影响和下一步清清楚楚。一段到底，句式：

`【严重程度·已遏制】{资产定位}发现{攻击定性·用业务语言}，已{按住方式}，未造成/是否扩散+影响。处理详情：已{MSS已完成动作}；建议/下一步{客户最小项}。`

示例（银狐木马，与「成品示例 · 示例 1」第一段为同一文本）：

```
【高危·已遏制】核心资产 个人PC DESKTOP-4LOACFG 发现银狐木马执行，已自动阻断外联，未造成进一步危害。处理详情：已封禁恶意IP 1个、域名1个，恶意文件 MD5 已加入 NGES 黑名单；建议上机清理伪装计划任务并修复被禁用服务。
```

**凝练版硬性要求**：

1. 首词即严重程度+已遏制结论（业务定性词准确，承接 §5.1 结果前置）；
2. 明确主体（哪台资产/哪个业务被波及）+一句“攻击是真的”（用研判结论的一句话，不带内部黑话）；
3. “已被按住”：写明按住方式（自动阻断外联/终止进程/封禁 IOC/隔离样本，结合处置详情）；
4. “没扩散”：给影响面判定（单机/是否全网扩散），**以 `*_全网排查.md` 的排查结论为准**（未扩散写“未发现其他主机命中”，扩散写“已发现 N 台主机命中，均已处置”），能枚举的列已封禁个数；
5. “影响+下一步”收在句尾：本事件影响一句话 + 需要老师做的最小下一步项（承接处置两栏）；
6. 一句话一段，面向客户可扫读，不堆技术名词罗列；整段为一个代码块/文本。

两段均在同一 `*_推送文案.md` 内，第一段在上方；对外发送时两段先后一并发出，详情=第二段详版。

### 5.3 详版正文硬性要求

**A. 结构定式（不可省、不可乱序）**

1. **通告抬头必带且结果前置**：置顶【深信服 安全事件通告】块，标题与字段严格按 §5.1 抬头字段规则表。
2. **事件概述 = 关键时间线，只讲与攻击直接相关的关键时刻+行为**：编号列表，每条=时间点+该时刻的关键动作；跳过/合并与攻击无关的铺垫（接收文件等如非必要不展开系统内幕），末句落到当前处置/危害状态，全段精炼不长篇。
3. **事件研判分两段证据：静态特征分析 + 动态（已执行）行为**：先一句定性（客户可懂的自然语言），再 `静态特征分析：`（签名滥用/白加黑/随机路径/文件名伪装等；**无静态特征证据就不写该段，不写空标题**），再 `动态行为（木马在主机上已执行）：`（持久化/加白/删卷影/禁更新/外联C2等逐条给实体与指令）。

**B. 研判危害陈述**

4. **危害如实、结合业务讲清（不夸大不隐瞒）**：确需描述危害时，在【事件研判】末尾单列一段，按客户所属业务关联具体可感知影响（如该样本会窃取浏览器 Cookie/账号、拖走涉发票报销/财务数据、或可被远程控制/横向扩散），基于情报与攻击链事实陈述；**不夸大不隐瞒**——有实据的后果写明，无实据的不可危言定性（不写"业务严重瘫痪/必然数据泄露"式臆断），也不因已拦截而过早断言"绝对无影响"。
5. **不承诺、不写死**：没有溯源到的入口写"建议排查"，不虚构下载来源；处置状态以人工/平台确认为准。

**C. 遏制&处置（两栏 + 归位规则 + 克制原则）**

6. **强约束分两栏**：`深信服MSS已完成：` 与 `需要老师处置内容：`。MSS 栏按**两条带标题子项**展开：`1. 威胁实体遏制：`（[已遏制] 封堵 C2/恶意域名/IOC + 黑名单、情报监测同步、可联动识别同源变体）与 `2. 全网排查：`（[已处置] **取自 `*_全网排查.md` 的一句话总结**，如“已对全网排查，未发现其他主机命中”/“发现 N 台主机命中，均已处置”）；若某子类本事件无实据（如仅单机无全网排查必要），省略该子项，不写空标题。
7. **待处置/兜底动作归属规则**（结合情报遏制范围，先分类再归位）：
   - **威胁实体遏制**（C2 IP/域名/URL/恶意 hash）：防火墙/端点封堵、加 NGES 黑名单 → **归「深信服MSS已完成」**（情报【影响评估】说明可放心阻断的才写）；
   - **关联资产全网排查**：**必须**由 §4.2 的 `telemetry-entity-hunt` 对该事件最需调查的 IOC 实际执行，结论**做一句话总结**写进「深信服MSS已完成」第二点（材料取自 `*_全网排查.md`），如“已对全网排查，未发现其他主机命中”/“已对全网排查，发现 N 台主机命中”；**未实际执行排查不得写“已全网排查”**；
   - **隔离/查杀**（恶意文件已由 NGES 自动隔离）：归「深信服MSS已完成」[已遏制]（如“已隔离但可能复发”则把根除/清理移到客户必办项）；
   - **客户必办且必要项**（终归「需要老师处置」，≤2~3 条）：删除恶意目录/原始投放文件、移除持久化项（计划任务/服务/启动项/Run键/Defender 排除项/禁用的更新服务，如确需手工整修）、必要时账号密码重置、入口溯源宣导；
   - **默认不推客户的兜底/服务方动作**：全盘扫描、病毒库入库、持久化主动自查、扩展排查等——除非确需客户配合，默认由 MSS 侧执行或作为“可提供协助”，不当作客户待办堆积；
   - 入口/除根未溯源到的 → 写“建议排查下载记录/IM 渠道/同网段”，不写死结论。
8. **客户栏极简**：`需要老师处置内容：` 仅列最精的、易上手的关键动作，≤2~3 条，[待处置]；已隔离/已清除/已封堵/已全网排查的项标 [已处置]/[已遏制] 并归入 MSS 栏；不写泛泛之谈（"全盘查杀""定期加固""建议加强防范"）与明显重复项，同类收敛为一条；“还能提供什么协助”（上机根除/二次核查）放收尾一句，不当作待办堆叠。

**D. 语言与合规**

9. **不堆内部技术标签与系统内幕**：面向客户正文不抛内部标签/黑话（如"black/gray TAG"、"Riskware 家族"、"Agent.uyyg" 家族代号当结论），也不罗列系统内部进程叙事（谁用 dllhost/svchost 拉起、签名内幕、"主机已装 NGES 属重点防护"等系统声明）；改用客户可懂的自然语言描述（"威胁情报已标记该程序为恶意木马"、可提"伪装打印工具诱导运行"），家族名最多作括号佐证，不让内部定性/系统实现做结论句。
10. **专业听得懂**：技术细节保留（路径/任务名/端口/MD5/时间/账号），但用一句业务语言解释"对客户意味着什么"；术语首次出现给通俗说明（如"持久化=开机自启，删除不彻底极易复发"）。
11. **给证据**：时间点、实体名、MD5、C2、路径、账号写全，支持客户拉群向业务部门复述。
12. **分点叙述**：建议 1、2、3 分点，避免小作文式长段落（概述/研判用编号列表更清晰）；全文避免浮夸形容词（"严重威胁"可改为具体后果）。
13. **开篇给业务定心/状态**：开场紧承概要后第一句即用业务可读表述讲清"现在到底怎样、对我的业务有无影响"（如"该恶意程序/外联已被 NGES 拦截/查杀，并未对您/系统造成危害"，或尚未拦截则如实写"正持续关注需配合处置"），不只堆技术动作；突出"已检出→已拦截/隔离→已在全网排查→持续监测"，让客户感受到响应快、免打扰。

**E. 特殊场景**

14. **多主机/复发事件**：开头一句总览（N台主机共N起，与之前事件同源/复发），单事件已处置动作在相应事件下标注。
15. **开场定式**（可选）：时间 → 发现{资产类型} {业务/资产名}（{IP},账号{账号}）{一句话概要} → {既成处置+消解句}（"已被…拦截/查杀,未对您造成危害" 或 "正持续告警需关注"）；需含业务信息（个人PC/服务器、是否核心、账号）。与通告块同义时不重复，见 §5.4 去冗余清单。
16. **低价值场景的默认文案**：若判定为"不推送"但需要告知客户（如广告组件），输出轻量说明（一句话事实 + 无危害结论 + 观察建议），不按上述板块展开。

### 5.4 去冗余裁切清单（净化通告块之下正文；单事件适用）

- **去冗余·一文一义**：通告抬头块已承载事件名/类型/IP/危害结论等关键信息，正文各板块不重复复述抬头已列字段，也不在板块间重复同一结论。开场定式句（尊敬的…）与【事件概述】第1条讲的是同一句概要、【事件概述】落点与【事件研判】危害段会出现同一句"已被拦截/未造成危害"——原则是同义结论只出现一次、后出现的位置必须叠加**新证据或新维度**才保留，纯重复一律删。洁净的单事件文案可直接从通告块切入编号概述+研判，语句密度高、少打扰。
- 通告抬头块已含"影响业务/资产类型+IP/危害结论"→ 开场定式的"尊敬的…{资产类型}{业务/资产名}({IP})"概要句，若与抬头重复且【事件概述】第1条已续写动作，则该长导入段可整段砍掉，通告块直接接编号概述；确保留开场时，压成一句时间+事件+消解，不复述抬头字段。
- 【事件概述】做"发生了什么"的客观事实时间线（时间+动作），【事件研判】做"为何恶意+何危害"的判定——两板块职责不重叠；概述末句的"已被拦截，未受影响"结论，研判危害段若再给同义句，则二选一，保留在研判危害/处置段更合理。
- 危害说明不必自成一段时并入攻击意图点后，但被合并段须同主题、且阅读转折完整；若并入造成一段多义，宁独立成段，不因拼行而牺牲可读。
- 收尾"可提供协助"与"需要老师处置[待处置]"不冗余：客户已能自行动手的最小项留待处置；如需 MSS 上机/复查才写收尾协助一句，非强推。

### 5.5 处置问询（独立步骤，主动向客户获取实际处置动作）

初版文案按「深信服MSS已完成 / 需要老师处置」两栏组织后，**skill 必须主动向客户发一次处置问询**，确认实际已完成的处理并回填，不能停留在未定稿状态。问询目的是：确认 MSS 侧主动处置（封堵/全网排查）是否有遗漏、并明确客户需动手的最小项。

**默认问询话术模板**（可直接发送）：

```
关于本次事件，MSS 已完成：{封堵 C2/IOC、恶意文件隔离等；全网排查结果}。
若属实，现需确认您侧是否已完成或将处理以下项，以便同步处置状态：
 ① 上机清理（删除 {恶意目录/文件/原始投递文件清单}）
 ② 移除持久化（删除计划任务 {名称}、移除 Defender 排除项等，如确需我方远程协助整修请告知）
 ③ （如有）重置受影响账号密码并核实异常登录
 ④ （如有）定位入口来源（下载记录/IM/邮件）并剔除隐患
以上均未做、需我方远程协助处置根除，也请直接告知。
```

**执行约定：**

- 人工已完成处置动作经对话/`--done` 提供后回填到对应栏；未提供 MSS 侧动作时不得留占位——先列出已明确自动处置（如 NGES 隔离/封堵）为 [已遏制] 项，其余必办项进「需要老师处置」保留 [待处置]。
- 问询必须在推送给客户前（或同步）发出；以客户/服务经理反馈处置动作＝唯一事实来源回填两栏。
- 客户未答复前，MSS 主动处置已知晓（NGES 自动隔离/C2 封堵）可先列为已遏制项，不臆造未证实动作；确需客户动手项保留[待处置]。
- 收到答复后：把已确认项移至对应栏，剩余保留，更新 `*_推送文案.md`（必要时同步 `*_推送判定.md`）。

### 5.6 情报截图证据（ti-redirect-analyze）—— 后台生成并归档（必做，非可选项）

**触发时机（必做）**：只要判定为「推送」且解析子文件中存在已确认恶意的 IOC，推送文案生成/定稿后（含处置回填后的终版）立即调用 `ti-redirect-analyze` 生成情报截图，并把截图作为追加证据归档到事件文件夹。不得等待用户再次提出要求才补做。

**展示约束**：TI 原始整页截图和 `*_情报截图证据.md` 只落盘归档，不在聊天中展示；每张归档后的 TI 摘要截图必须在最终回复中用 `MEDIA:<summary_screenshot>` 输出，并与推送文案代码块同轮返回。不得输出“无命中情报可截图”等额外说明。

触发对象（硬性门禁）：**只对 GPTRawLog 解析子文件中已经有恶意定性依据的 IOC 调用 `ti-redirect-analyze`**，包括 `threatList` 命中且定性恶意的实体，以及 `gptResponse.maliciousEntities` 中的恶意实体。

不得对以下实体调用：

- 解析子文件没有恶意依据的实体——跳过，不留空图；
- 仅出现在行为树、未命中威胁情报的“事件其他实体”；
- 已被人工判为误报/无关的实体（如无关的 Edge 自启动项等系统常规项）。

若有 N 个实体命中，则为每个命中实体各生成一张截图；无一命中则不调 ti-redirect-analyze、不产出截图。

**执行方式（按 `ti-redirect-analyze` SKILL.md）**：

1. 判 IOC 类型（domain/url/ip/md5）；`flclashcn.com` → domain。
2. 运行 `python scripts/run.py --type <type> --ioc <ioc>` 得到重定向 URL。
3. 用 browser 打开该 URL，等待 SPA 渲染约 8s，确认落到 `analysis-platform/*_report/<b64>` 报表页。
4. 窗口宽 1400、fullPage 截图；按子 skill 给出的分型裁剪坐标截报告摘要区（domain/url/ip vs md5 不同），确保图中含标题 + SANGFOR标签 + 威胁等级/时间 等要点；布局偏移时按摘要元素 getBoundingClientRect() 重取坐标。
5. 取得 browser 工具返回的截图路径后，运行 `ti-redirect-analyze/scripts/archive_screenshot.py --source '<截图路径>' --event-dir '<本 skill 的 run.py 返回的 event_dir>' --type <类型> --ioc '<IOC>'`。由脚本保存原始截图、裁剪摘要图并追加证据文件；不得用 `Write`、`Edit` 或 `apply_patch` 直接写 `${SKILL_OUTPUT_DIR}`，否则 Runtime Guard 会按设计拒绝。

**产物落盘**：归档脚本在事件文件夹内保存每个 IOC 的原始截图和裁剪摘要图，并新增或追加 `*_情报截图证据.md`，记录截图文件名与 TI 关键字段（标签/等级/信誉/危害描述），供解读与追证。截图正文不插入长图片 URL 清单。**落盘路径与文案同在一事件文件夹，便于整文件夹归档。**

> 若平台页面未登录仍可见报告摘要，直接截图即可；TIP：同一批事件多个命中 IOC 依次截图，不在循环里高频重开页面。

### 6. （可扩展）事件归档卡片 + 最终输出

可将推送文案浓缩为 `*_推送卡片.md`：事件名、时间、主机、定性、关键IOC、处置状态、证据清单（截图/MD5/C2/时间点），用于内部归档。全部产物（原始日志、中间过程、推送材料）保留在事件文件夹中，**不删除**。归档卡片、事件文件夹路径、判定结论和待人工确认项均不得出现在最终聊天回复中。

**最终交付**：读取每次归档返回的 `summary_screenshot`，逐行输出 `MEDIA:<绝对路径>`；随后读取定稿后的 `*_推送文案.md`，将全文原样放入一个无语言标记的 Markdown 代码块并立即结束回复。除这些 TI 摘要图和文案代码块外保持零文字、零链接；不得添加开场、标题、解释、摘要或收尾。

本 skill 的终点是生成推送材料，并按“TI 摘要截图 + 唯一文案代码块”的合同同轮返回，不调用企微发送接口，不自动把内容发给客户。是否发送以及发送到哪个会话由用户另行决定。

## 高价值推送文案规范总结（要点索引 · 完整规则见 §5）

- **两段式推送**：每次对外推送先发第一段凝练话术（首词=严重程度+已遏制结论，让客户一眼看出“攻击是真的、已被按住、没扩散、影响/下一步清楚”），再紧跟第二段标准详版（默认格式不变）。模板与要求见 §5.1 / §5.2。
- **通告抬头块**：标题 `【深信服 安全事件通告】{已遏制结论}`（如 `已遏制，未对系统造成实际危害` / `已遏制，存在残留待处置`）；主体字段依次为 事件名称/事件类型/事件ID/影响业务/资产信息/告警来源/组件检出时间/业务危害；**影响业务包含主机名称、资产组、资产类型、MAC地址、账号五要素**，按 `{IP}(主机名称：…、资产组：…、资产类型：…、MAC地址：…、账号：…)` 拼接；**告警来源为 NGES 时固定写 `NGES`**，其余按实际来源写；业务危害=一句简洁业务消解句（如“该木马已被 NGES 实时拦截，未对您的系统造成实际危害”）。阅读排序：结果（大不大/已拦）→ 要不要动 → 发生了什么。字段不臆造，缺值用 `-`。字段取值与缺省规则统一见 §5.1 抬头字段规则表。
- **正文四板块**：开场定式（可选）→ 事件概述（关键时间线）→ 事件研判（定性 + 静态/动态两段证据链 + 危害如实）→ 遏制&处置（MSS/客户两栏，客户栏 ≤2~3 条）。逐条硬性要求与归位规则见 §5.3，去冗余裁切见 §5.4。
- **全网排查（§4.2）**：判定「推送」后，对最需调查的 IOC 调 `telemetry-entity-hunt`，结果落 `*_全网排查.md`，在【事件遏制&处置】第二点做一句话总结（如“已对全网排查，未发现其他主机命中”）。
- **禁用**：无证据的定性（未溯源到入口就写"从xx下载"）；模糊处置（"已处理"无具体动作）；内部标签当结论句；系统内幕进程叙事；需求外低效繁琐操作堆积；夸大/隐瞒危害。

**说明**：以上要点为索引，字段拼接、句式、证据链、两栏写法与裁切规则均以 §5.1–§5.4 正文为准。
