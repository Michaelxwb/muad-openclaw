# 监控 MSSP 平台事件

本 skill 用于：监控**用户明确指定的客户**在 MSSP（SOAR）平台**用户明确指定时间范围**（指定起止时间或最近 N 分钟）内的安全事件（仅未处置/处置中/定期跟进），**不做去重**，逐条展示事件明细与关联告警。它是可独立上传、可由外部定时任务反复调用的单次监控能力；查询和展示结束即结束，不等待 CGID、不查询 GPTRawLog、不执行深度分析，也不生成推送文案。

> 本 skill 只绑定 **mssp**（SOAR）平台。MSSW 尚未实现；用户明确要求 MSSW 事件监控时，不得调用本 skill。登录态由 muad（session-manager）代管，脚本经 `shared.get_cookie()` 自动取得，**无需也不得手动粘贴 Cookie**。业务 API origin 由 `config/api_config.json` 的 `platforms.mssp.origin` 决定（可用环境变量 `MONITOR_MSSP_BASE_URL` 覆盖）。输出结论直接回复到聊天，不写文件。

> **关键：mssp 请求头必须带平台固定头** `X-CSRFToken`（固定值，见 `config/api_config.json` 的 `platforms.mssp.fixed_csrf_token`）+ `timezone`（+08:00），否则接口返回 403 / code 9064。event_table 必须传**完整查询体**（含 company_id/order/offset/limit 等），仅传 create_time 会返回 code 9064。

## 定时任务调用约定（外部定时器驱动，强制）

本 skill 是**一次性单次监控能力**，自身不带调度逻辑；“多久跑一次”必须由外部定时器（openclaw cron）驱动。建定时任务时必须遵守：

- **必须用 `--session main` + `--system-event`**：main 会话继承当前用户的绑定身份，输出与后续追问都落在同一会话上下文里。
- **禁止用 `--session isolated`**：隔离会话没有绑定上下文，会把「当前账号尚未绑定，请联系管理员获取绑定码，然后发送 /bind <绑定码> 完成激活」当成回执发出，属于错误投递。
- **禁止用 `--command` 直投 run.py**：其 stdout 不落会话上下文，用户后续无法点名「事件 N 生成推送话术」，会断掉 `mssp-event-push-content` 流程。
- 无事件也要发时，命令必须带 `--notify-no-event`。
- 窗口用 `--minutes N`（最近 N 分钟），不得用 `--start/--end` 手算替代。

正确示例（每 5 分钟、最近 5 分钟窗口、无事件也发）：

```bash
openclaw cron add --name "mssp-monitor-<客户简称>-5m" --every 5m \
  --session main \
  --system-event "【定时任务·MSSP事件监控】读取 /opt/openclaw-skills/monitor-mssp-events/SKILL.md 并执行：对 <完整公司名>(company_id <数字ID>) 跑 --minutes 5，必须带 --notify-no-event；不做终端GPT 索要 CGID / 推送，等用户后续点名事件再处理。" \
  --channel wecom --to "<会话ID>" --timeout-seconds 600
```

> main 会话的 payload 必须用 `--system-event`（`--message` 会报 `Main jobs require --system-event`）；`--announce/--no-deliver` 只对非 main 目标有效，main + announce 会报错。

## 触发词

监控 MSSP 事件、监控 mssp 平台事件、看指定时间有没有新事件、有没有新增事件、查看最近事件、终端GPT事件

明确排除：MSSW 事件监控当前未实现，不得将 MSSW 请求路由到本 skill。

## 强制用户旅程

以下旅程是本 Skill 的执行合同，必须按顺序完成，不得跳步、合并或自行改写。用户只发出“监控事件”等宽泛指令时，不能直接查询平台。

### 旅程 1：收集监控范围

开始任何平台调用前，必须从用户本次对话中明确获得：

1. 要监控的一个或多个客户。
2. 时间范围，二选一：
   - 指定起止（如“9月5号到9月8号” → `--start 2026-09-05 00:00 --end ...`）；
   - 最近 N 分钟（如“最近10分钟” → `--minutes 10`）。

门禁规则：

- 两项齐全：进入“旅程 2”。
- 缺少客户：只询问要监控哪个客户，然后停止。
- 缺少时间范围：只询问要监控哪个时间范围（指定起止 或 最近多少分钟），然后停止。
- 两项都缺少：一次性询问客户和时间范围，然后停止。
- 不得使用配置中的客户、历史选择、记忆客户、默认客户或默认时间范围补齐缺失项。
- 门禁未通过时，不得获取登录态，不得调用客户、事件、资产或告警接口。

### 旅程 2：确认客户

- 使用者可以输入客户简称或完整名称，但这一步只能通过独立解析脚本执行。
- 运行以下命令后，只展示候选客户的完整 `company_name` 和真实数字 `company_id`，不执行事件监控：

```bash
python3 scripts/resolve_customer.py --company "<客户简称或完整名称>"
```

- 只有使用者明确确认候选客户后，才能把对应数字 `company_id` 交给“旅程 3”。
- 存在多个候选、找不到客户、缺少完整名称或缺少数字 ID：停止旅程，不得自行选择或继续监控。

完整名称是强制不变量：从客户确认完成开始，监控客户列表、查询失败客户、事件明细中的“客户”以及任何涉及客户的文字，都必须使用平台返回的完整 `company_name`。禁止显示使用者输入的简称，禁止只显示 `company_id`。事件明细中另以独立字段“公司 ID”展示平台数字 `company_id`。

### 旅程 3：执行事件监控

客户已通过旅程 2 明确确认、且时间范围已收集后，运行入口脚本（时间范围二选一）：

```bash
# 方式A：指定明确的起止时间（YYYY-MM-DD HH:MM 或 HH:MM:SS，支持分钟级，如 10:50 ~ 11:00）
python3 scripts/run.py --company-id "<已确认数字company_id>" --start "<起始时间>" --end "<结束时间>"
# 方式B：最近 N 分钟
python3 scripts/run.py --company-id "<已确认数字company_id>" --minutes <正整数分钟>
```

**无事件输出控制（强制）**：本 skill 默认**无事件时不输出任何内容**（stdout 为空）；只有当使用者明确要求“无事件也要说一声”时，才加 `--notify-no-event`，此时无事件会输出「当前无事件。」。使用者未指定时，一律默认静默（不输出）。

- 无事件 + 未指定 `--notify-no-event`：脚本不输出任何内容（退出码 0），Agent 也不再补充任何“无事件”文案（守静默）。
- 无事件 + 指定 `--notify-no-event`：脚本输出含「当前无事件。」的 Markdown 代码块，Agent 原样转发。

**时间与参数口径（强制）**：

- 使用者以 `YYYY-MM-DD HH:MM[:SS]` 输入的时间是**东八区（+08:00）本地时间**，脚本按东八区解释并换算成 UTC 毫秒时间戳，再放入请求体 `create_time: [start_ms, end_ms]`。例如 `2026-09-11 00:00` → `1789056000000`、`2026-09-11 23:59:59` → `1789142399000`，与平台页面查询 9 月 11 日 0 点至 23:59 传参一致。禁止把东八区输入当作 UTC 解释（会导致整体偏移 8 小时）。
- 时间粒度支持**分钟级**：`HH:MM` 与 `HH:MM:SS` 均可，可用于“近 10 分钟/最近 N 分钟”等窗口，不得把分钟级请求降级为小时级。
- “最近 N 分钟”一律用 `--minutes <N>`（`startTs = now - N*60*1000`，`endTs = now`），不得借用 `--start/--end` 手算替代。
- 请求体里的时间戳一律为 UTC 毫秒戳，但**所有回国展示的时间（监控窗口、组件检出时间等）一律按东八区（+08:00）渲染**，不得显示成 UTC。
- 事件表请求体必须为**完整查询体**（company_id / order / offset / limit / create_time / asset_type / event_status 等），`create_time` 为 `[起始毫秒, 结束毫秒]`；仅传 create_time 会返回 code 9064。

监控多个客户时，为每个客户重复传入 `--company-id`。脚本会用已确认 ID 精确回查平台完整 `company_name`，再按用户指定时间范围查询事件。**:范围查询默认只拉取状态为 未处置(inited)/处置中(disposal)/定期跟进(suspend) 的事件，且不去重，范围内查到多少展示多少。**

事件查询前必须执行第二层校验：传入事件、资产接口的 `company_id` 必须是已确认且平台回查成功的纯数字 ID。发现简称、客户名称、空值或其他非数字内容时立即停止，不得发起后续查询。

### 旅程 4：补齐事件信息

每个新增事件必须依次补齐：

1. 事件基础信息：客户、**tenantId**、事件 ID、**组件检出时间（取 event 接口的 `checkout_time`，原样展示 `YYYY-MM-DD HH:MM:SS`；缺失显示 `-`）**、主机 IP。事件名以事件块头部动态标题行 `事件N：「事件名」` 展示，不作为独立字段行。
2. 资产与业务信息：**逐行独立展示**，固定顺序为主机名称、资产组、资产类型、MAC地址、设备覆盖、业务名称、业务等级。
3. 处置状态：取事件表的 `event_status` 原始枚举，**必须翻译为中文展示**：`inited→未处置`、`disposal→处置中`、`suspend→定期跟进`，未知/缺失显示 `-`。禁止展示 inited/disposal/suspend 等英文枚举值。

资产字段优先取资产接口，事件表字段作为补充；**资产类型若平台返回 `unknown`（或其他未识别值），统一展示为中文“未知”**；“业务等级”只取资产接口返回的 `business_level`，按 `1=核心`、`2=重要`、`3=一般` 映射，缺失或其他值显示 `-`。平台未返回的基础字段使用 `-`，不得猜测或编造。数据源、NGES 安装状态和终端 GPT 判断只用于内部生成“事件分类”，不得作为独立字段展示。

**tenantId（客户级字段）**：每个客户查一次 `GET /gateway/customer-mgr-service/order/v1/branch/dev?_method=GET`，请求体 `{"order":"asc","offset":0,"limit":100,"keyword":"","type":69,"status":0,"company_id":"<数字company_id>","platform_type":"scloud","belong_local_xdr":0}`，取 NGES 设备的 `gateway_id` 作为 `tenantId`；同一客户下所有事件展示同一个 `tenantId`，缺失显示 `-`。

**不展示 IOC 字段**：IOC（ioc_grouped/ioc_value）不再作为独立字段输出，即使平台返回了 IOC 也不展示。仅“关联告警”和“事件分类”在资产信息之后展示。

### 旅程 5：事件分类

以下条件用于内部判断，对外只输出冒号后的完整分类描述，禁止输出“场景 1/2/3/4”等内部编号：

- NGES 数据源且关联告警标题包含“通过”：`终端GPT检测生成了对应事件，具有终端GPT对整个事件的研判分析（重点价值推送）`。
- NGES 数据源且无“通过”告警：`杀毒引擎上报事件`。
- 非 NGES 数据源但主机已安装 NGES：`数据源非NGES事件，但主机安装了NGES`。
- 非 NGES 数据源且主机未安装 NGES：`数据源非NGES事件，同时主机未安装NGES`。
- 关键接口或关键字段缺失导致无法判断：`关键数据缺失，暂无法完成事件分类`。

“事件分类”必须是每个事件的最后一个字段。关联告警在业务信息之后、事件分类之前展示；多个事件之间用 `--------------------------------------------------------`。

**关联告警取值优先级（本 skill 展示用）**：从该事件 alarm_list 中选取“关联告警”字段要展示的条目，优先级：

1. 优先取 `key_alert == true` 且标题含“通过”的告警；
2. 若上者为空，则去掉 `key_alert` 条件，取所有标题含“通过”的告警；
3. 若仍为空，兜底取全部告警。

展示集合确定后，“关联告警”字段逐条列出该集合，但**“共N条关联告警”中的 N 必须为该事件全部告警的总条数（不是展示集合的条数）**，即把筛选掉的其它告警也算在内；展示集合为空时整个字段省略。判定“事件分类”的 `is_gpt` 仍只看是否存在含“通过”的告警，不受 `key_alert` 筛选影响。

### 旅程 6：输出到聊天

- 直接将脚本生成的单个 Markdown 代码块回复到聊天。
- 必须保留动态标题（`事件N：「事件名」`）、汇总分隔线、各字段行、字段顺序、对齐空格和事件分割线。
- 资产与业务信息必须逐行独立展示（主机 IP、主机名称、资产组、资产类型、MAC地址、设备覆盖、业务名称、业务等级），不得合并成“资产信息/影响业务”行。
- 不输出场景统计汇总，不输出“场景几”等内部编号。
- 不使用表情符号、Markdown 表格、竖线分隔或卡片格式。
- 不在代码块前后增加摘要、解释、提示或二次结论。
- 禁止在代码块外使用客户简称生成“某某客户无新增事件”等二次总结。
- 监控客户列表、失败客户和事件明细中的客户名称必须全部使用平台返回的完整 `company_name`；事件明细中另以独立字段“公司 ID”展示数字 `company_id`。
- 关联告警必须使用独立的“关联告警”字段逐条展示；仅在实际存在告警时显示，没有告警时省略整个字段。
- 没有失败客户时，完全不显示“查询失败客户”。
- 存在失败客户时，只显示实际失败的客户；不得把查询失败解释为无新增事件。
- 多个事件之间使用一条 `--------------------------------------------------------`；单个事件不显示事件分割线，最后一个事件后不显示分割线。
- Agent 不得重新组织、压缩、扩写或润色脚本输出。

### 旅程 7：对终端GPT事件自动索要 CGID 与可选 Webhook

事件明细代码块发出后（旅程 6 结束），对**事件分类为“终端GPT检测生成了对应事件，具有终端GPT对整个事件的研判分析（重点价值推送）”**的事件，执行以下自动化流程：

1. 逐个（或合并）向用户索要对应事件的 CGID（一个事件一个 CGID）；**仅索要缺失的 CGID，不得要求用户重复提供已在监控结果中的事件 ID、客户、事件名、主机、资产业务信息和处置状态**。
2. **在同一条索要消息里，额外询问用户是否要提供企业微信机器人 Webhook 链接**（可选，不是必须），用于把这批事件的推送结果实时发送到群。说明：提供则按“一个事件完成即推送一条”的实时方式送达；不提供则跳过 webhook 推送，仅在聊天里回传推送材料。**不得把 webhook 地址当成必填项，也不得因为用户未提供就卡住流程。**
3. 用户提供 CGID 后，**自动执行** `mssp-event-push-content` 子 skill，把该事件的事件 ID、客户、事件名、主机、资产、IOC、关联告警和处置状态组装为 `--event-context-json` 一并传入，无需用户再重复输入额外上下文。
   - **若用户本轮提供了 webhook 链接**，必须把它透传给生成推送的子 skill：在传给 `mssp-event-push-content` 的 `--event-context-json` 中增加 `webhook_push: true` 与 `webhook_url: "<用户提供的 webhook 地址>"` 两个字段；由该子 skill 的送达动作（`scripts/send_webhook.py`）负责逐事件推送。**本 skill 自己不得直接调用 webhook 或自行发送**，只负责把链接按约定转交。
   - **若用户未提供 webhook 链接**，不得虚构或默认填入 webhook 字段，按子 skill 默认流程（仅回传聊天推送材料）执行。
4. 多个终端GPT事件时，对每个已获得 CGID 的事件分别执行；未提供 CGID 的事件暂停等待，不阻断其余事件。
5. 非终端GPT分类（如“杀毒引擎上报事件”“数据源非NGES事件…”）的事件不自动索要 CGID，也不自动执行推送，等待用户后续明确点名处理。

## 平台执行细节

脚本自动完成以下步骤：

### Step 1 — 拉取时间段内的事件表
调用 MSSP 事件表接口，入参 `create_time: [startTs, endTs]`（UTC 毫秒时间戳），获取该时间段内的事件列表。

- 指定起止（`--start/--end`）时：由东八区输入换算得到的 UTC 毫秒戳直接作为 `[start, end]`，支持分钟级。
- 最近 N 分钟（`--minutes`）时：`startTs = now - N*60*1000`，`endTs = now`。
- 事件表接口（公网）：`https://soar.sangfor.com.cn/gateway/event-mgr/external/event_table`（脚本内由 `config/api_config.json` 的 `endpoints.event_table` 提供）
- **必须传完整查询体**：company_id / order / offset / limit / create_time / asset_type / event_status 等，`create_time` 填毫秒时间戳区间；仅传 create_time 会 9064 无效的输入。
- 若事件列表为空 → 默认不输出任何内容；仅当启用 `--notify-no-event` 时输出「当前无事件。」，结束。

### Step 2 — 逐个新增事件，收集关联告警并完成内部分类
对每个新增事件，取事件 `event_id`，调用事件详情的告警列表接口：

- 接口：`/gateway/alarm-mgr/v1/event_table/alarm_list?_method=GET`
- 请求体：`{"order":{"latest_time":"desc"},"offset":0,"limit":10,"event_id":"<事件ID>"}`
- 判断：返回体的告警条目中，`title` 字段若包含 **"通过"** 二字，仅用于内部生成“终端GPT检测生成了对应事件，具有终端GPT对整个事件的研判分析（重点价值推送）”分类；对外不输出“终端 GPT”独立字段或内部场景编号。关联告警存在时，作为独立字段逐条展示。

### Step 3 — 汇总输出
对每个新增事件输出完整基础信息、资产与业务信息、事件分类，以及实际存在的关联告警。资产字段优先取资产接口，事件表字段作为补充。

## 执行纪律

1. 脚本报错直接退出（exit≠0，错误走 stderr），不自行修改、不尝试修复。
2. 登录态由 session-manager 代管，绝不手动粘贴 Cookie，绝不打凭据到日志。
3. 时间戳统一用**毫秒**；请求体 `create_time` 用 **UTC 毫秒戳**（当前时间用脚本内 `int(time.time()*1000)` 计算）。东八区 `YYYY-MM-DD HH:MM[:SS]` 入参经 `parse_dt_ms` 按 +08:00 解释后换算为 UTC 毫秒戳，**不得使用 `calendar.timegm`**（会偏移 8 小时）。所有对外展示的时间均按东八区渲染。
4. 终端GPT判断只输出「是/不是」，如用户单问某个事件，直接回答。
5. 未收集到明确客户或监控时长时，直接询问缺失项并停止，不得调用登录态、客户、事件、资产或告警接口。时间范围一律用“指定起止 `--start/--end`”或“最近 N 分钟 `--minutes`”，禁用 `--hours`。
6. 客户简称/完整名称只能进入 `resolve_customer.py` 的搜索参数；`run.py` 的 `--company-id` 只能接收旅程 2 返回并由使用者确认的数字 ID。
7. 事件、事件详情、告警和资产接口的关联 `company_id`、`event_id`、主机 IP 等参数，必须来自平台响应中已校验的字段或前置旅程的可信值；不得用展示名称、输入简称或未校验字段替代。接口响应中的候选客户、事件、资产和告警条目必须先校验为对象及所需字段，再参与后续请求或分类。
8. 旅程 7 索要 CGID 时，必须**同时**询问用户是否提供企微机器人 Webhook 链接（可选项）。用户提供 webhook 时，只能通过 `--event-context-json` 的 `webhook_push: true` 与 `webhook_url` 字段转交给 `mssp-event-push-content`，由该子 skill 负责送达；**本 skill 不得直接发送 webhook**，也不得把 webhook 地址写入任何落盘文件。
