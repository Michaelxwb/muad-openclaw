## 2. 背景与目标

### 2.1 问题陈述

当前产品通过控制面配置和外置插件，把多个用户及其 Agent、模型、工作区、浏览器 Profile、技能和业务平台会话承载在同一 Pod 内。用户通过既有企微或 Mattermost 机器人进入自己的 Agent。

OpenClaw 主线在会话存储、插件 SDK、重启协议、默认跨 Agent 权限和任务恢复方面发生变化。直接替换基础镜像可能出现“DB 绑定未丢，但机器人消息落入错误 Agent”“Gateway 健康，但模型修改未生效”“升级失败后旧镜像无法读取新版状态”等情况。

本需求解决版本升级兼容与既有业务连续使用的问题。已有用户无需重建、原 Agent 不换 ID、原机器人不换账号。无法提前演练时，风险控制依靠代码与合成数据验证、可恢复的正式切换，以及切换后的真实边界验收。

### 2.2 目标与业务价值

| 目标 | 业务价值 | 验收依据 |
|---|---|---|
| 保留原机器人和完整用户绑定 | 用户继续使用原入口，无需重新绑定 | DB 保护字段逐条一致；机器人实际身份一致 |
| 保持单 Pod 多用户隔离 | 升级不串用户、模型、工作区或业务会话 | 全量路由校验与隔离用例 |
| 保留当前新增 Agent 与模型变更行为 | 控制面运营流程继续可用 | 配置生效、Gateway 重启及 generation 收敛测试 |
| 完成一次性版本切换 | 前置门禁全绿、切换一次成功；失败停 error 人工修复 | 门禁记录、技术校验与取证材料 |
| 为后续性能、记忆和长任务改进提供基础 | 在兼容完成后评估收益 | 后续项目独立验收；本次不承诺容量倍增 |

新版可能提供更好的并发处理、持久化、恢复与工具调用能力，但本次不把上游宣传或静态源码检查当成已实现的产品收益。新增 Agent 已有热重启能力，不将其重复计算为升级新增收益。

**成功指标**

| 指标 | 当前基线 | 目标 |
|---|---|---|
| 既有受保护绑定变化数量 | 正式切换前采集 | 0 |
| 有效既有身份路由覆盖率 | 正式切换前采集 | 100%，全部命中原 Agent，不能使用默认路由兜底 |
| 已禁用身份被重新放行数量 | 正式切换前采集 | 0 |
| 既有机器人账号替换、用户重新绑定次数 | 原账号及 DB 记录 | 0，升级流程不触发 |
| 双 IM 业务可用 | 当前启用账号清单 | 启用账号均完成切换后收发验收 |
| 升级过程人工迁移脚本/手工 SQL 步骤 | 无此设计 | 0，升级全程不得要求人工执行迁移脚本 |
| 管理员修改模型后的生效方式 | 需重启服务（2026-10-07 实测） | apply 路径自动触发 Gateway 重启并生效，不需要人工操作 |
| 容量与耗时 | 生产实际配置，未进行本次实测 | 保留现有上限；记录停机时间，不编造 SLA、提速比例或 50 用户容量 |

## 3. 用户与场景

- 已经绑定的终端用户：向原企微/Mattermost 机器人发消息，使用原 Agent 和原模型。

- 运维人员：在无法提前演练的条件下执行正式升级和失败恢复。

### 4.1.1 FEAT-01：固定版本与兼容清单

- 目标以明确的精确版本和可追溯镜像 digest 发布，不使用浮动 `latest`；版本线冻结为发布时的最新稳定版且不设同线备选。
- 构建、镜像标签、自检、CI 默认值、SDK 导入和浏览器依赖保持一致。
- 企微/Mattermost 插件的静态兼容检查与实际启动验收分别记录。
- 微信不纳入业务改造或收发验收；未启用插件不能因加载旧 SDK 而阻断双通道启动。
- 目标组合未确定或关键 API 不兼容时，不进入生产切换。

### 4.1.2 FEAT-02：DB 绑定保护

- 沿用原 Console DB，不实施绑定表结构迁移，不删除重建用户、Agent、Pod 业务记录。
- 保护原 `HumanUserID、PodID、AgentID、ModelConfigID`，以及身份的 `Channel、OpenClawChannel、AccountID、ExternalID、ExternalIDType、PeerKind、Status`。
- 保护原浏览器 Profile、端口、用户状态及模型配置内容。
- 对比稳定排序后的完整记录集合；数量相同不能代替逐条一致。
- 允许更新镜像标签、单调 generation、apply 状态和时间等运行字段，不把这些变化误判为绑定丢失。
- 保留禁用记录的原状态，不通过重新生成配置将其激活。

### 4.1.3 FEAT-03：原机器人复用

- 企微使用原 Bot ID 与 Secret，机器人配置解密所需主密钥保持可用。
- Mattermost 使用原服务器地址与 Bot Token，并核对 Token 对应的原机器人用户身份。
- 不因升级轮换 IM 凭据或创建新机器人；内部服务 Token 与 IM 凭据分开处理。
- 凭据失效或账号身份不符时，不能把“DB 绑定完整”标为“业务可用”。

### 4.1.4 FEAT-04：原位切换协调

- 切换锁覆盖目标 Pod 的配置、绑定、用户成员关系、模型变更和异步 apply。
- 目标 Pod 正式切换期间不允许新增、修改或消费绑定码；已有绑定保持有效。
- 处理正在执行的任务，暂停定时任务与新请求入口，再生成升级取证材料（停写后的状态离线副本）。
- 同一机器人不能由旧、新 Gateway 同时在线消费；采用停旧启新。
- 影响范围限于目标 Pod；只有一个生产 Pod 时就是该 Pod 的正式维护窗口，不假设存在灰度环境。

### 4.1.5 FEAT-05：升级材料取证（不提供回退）

- 升级前生成状态离线副本与 Doctor 原生 `*.pre-startup-migration-*.bak`，并记录旧镜像 digest 与启动输入，用于前置验证与故障取证。
- 迁移不可逆：9.8 起状态 schema 单向升级，旧镜像无法读取新状态，因此本次跨版本迁移路径显式关闭自动回退（allowRollback=false）。
- 既有回退语义（50205/50215 代表“已自动回滚”）在默认升级路径继续有效；仅迁移 opt-out 路径使用 50216 表达“停在 error 不自动回退”。
- 取证材料不放在将被替换的 Worker 卷内；权限与脱敏要求不变。
- 没有可用于前置验证的副本则 G-01 对真实数据不成立，只允许合成状态验证并明确更高风险，风险不可接受时终止升级。

### 4.1.6 FEAT-06：无感历史处理

- 升级全程零人工迁移脚本：历史兼容/迁移由目标版本内置能力自动完成，项目不提供也不要求一次性迁移脚本、手工 SQL 或手工清理。
- 旧会话与 transcript 不作为强制迁移成功项；原件至少留在取证材料中。
- 仅处理已明确识别的会话数据；不直接删除整个 PVC、`agents/` 或整个 SQLite 文件。
- 新会话继续使用原 Agent 和机器人；明确可能无法接续旧上下文。
- 用户工作区、私有技能、业务平台配置、长期记忆源文件与定时任务定义单独保护。
- 暂停无法兼容的定时任务并形成明确清单，不静默丢弃或以错误账号投递。
- 不要求旧版读取升级后新产生的会话；失败或中断造成的新会话差额须记录。

### 4.1.7 FEAT-07：配置与重启兼容

- 配置由原 DB 重新构建 desired DTO，经 schema 校验和原子写入，沿用 generation 机制。
- 适配新版 Gateway 重启协议，避免沿用已改变语义的信号。
- 新增用户/Agent 保持用户确认的热重启生效方式，不强制重建整个 Pod。
- 模型修改必须自动触发 Gateway 重启并按原模型绑定生效（2026-10-07 实测确认仅热加载不生效）；不得静默使用默认模型。
- generation 收敛之外还需校验运行时实际使用的配置及路由。

### 4.1.8 FEAT-08：多用户与业务资产保护

- 显式限制会话可见性与跨 Agent 调用，不继承更宽松的新默认值。
- 保留 Runtime Guard 的未知身份、跨用户工具、浏览器 Profile、文件访问、业务凭据及并发租约控制。
- 模型绑定保持独占，创建新用户仍要求未占用 `model_config_id`。
- 保留 system/public/private 技能分层与 system protected，不因升级静默覆盖私有技能。
- 新版任务恢复不能无条件重放可能产生业务副作用的工具操作。

### 4.1.9 FEAT-09：分层验收与可观测结果

- 分别输出：DB 保护字段结果、配置 generation、全量路由结果、通道连接结果、真实收发结果。
- 每条有效绑定在运行时命中原 Agent，不能靠默认 Agent 兜底；跨通道归属也保持一致。
- 真实收发在正式切换后进行，覆盖启用的每个机器人账号，并验证同 Pod 不同用户隔离。
- 无真实消息证据时只能记录“技术校验通过、业务验收待完成”，不能宣称全部可用。
- 验收消息须由运维或业务用户触发；文档产出本身不授权自动向外部发送消息。

### 4.1.10 FEAT-10：无演练条件下的回归

- 所有实施变更包含相应测试；使用合成绑定数据、真实临时 SQLite 和 fake/mock Driver。
- 自动化覆盖 API、Store、DTO、渲染、路由解析契约、重启选择、切换失败与 fail-forward 处理。
- 不把 mock 测试标为真实 IM、真实 Gateway 或真实 Docker/K8s 验证。
- 真正依赖生产账号的验证记为正式切换后的人工外部验收，并记录其原因。
- 不把生产副本、影子机器人、生产凭据克隆或提前回滚演练列为必需门槛。

### 4.1.11 FEAT-11：故障与中断处理

- 区分切换前拒绝、切换中失败、技术校验失败；失败停在 error，不自动回退，不返回“已自动回滚”。
- 记录切换阶段、取证引用和保护字段基线，使 Console 中断后可重建处理状态。
- 未完成的切换不能被自动 reconcile 当成普通配置更新继续推进。
- 后续请求不能并发覆盖正在切换或失败待处理的 Pod；修复后从 error 态出口继续（fail-forward）。
- 错误与审计脱敏，不输出机器人 Secret、Bot Token、LLM Key、Cookie 或完整配置。

### 4.1.12 FEAT-12：工作量与收益记录

- 按版本核对、兼容改造、自动化回归、正式切换验收分段估算。
- 人日与停机时间分开；没有演练数据时不承诺分钟级恢复或停机上限。
- 记录实际结果供后续优化；容量扩大、记忆增强、CodeMode 和技能自学习另外立项。

### 4.2 边缘情况

| 场景 | 预期行为 |
|---|---|
| 当前不存在有效用户路由 | DB 基线仍必须核对；显式记录 0 条路由，不虚报覆盖既有用户 |
| 同一用户同时绑定企微和 Mattermost | 两个身份仍归属原 Human User/Agent，沿用现有会话合并策略 |
| `AccountID=default` 或存在多个账号 | 保持原匹配语义，不擅自变成 Bot ID 或去掉账号维度 |
| 用户/身份已禁用 | 保留禁用；未知身份不得进入业务 Agent |
| 请求等待锁期间配置变更 | 持锁后重新读取基线，不能使用过期记录 |
| 拉镜像失败、取证材料生成失败 | 在安全阶段拒绝（未改写状态），不能留下假成功 |
| 历史格式不支持、磁盘不足 | 不能宽泛清理；保留原件并阻止不可恢复改写；不以人工迁移脚本作为出口 |
| 目标版本内置迁移失败 | 停 error 人工修复（不回退），不新增人工迁移脚本、不宽泛删库 |
| 管理员修改模型 | apply 路径自动触发 Gateway 重启并按原模型绑定生效，不需要人工重启 |
| 正式切换后无用户发消息 | 技术结果与业务验收分开记录，保持待验收 |
| 升级过程中 Console 重启 | 依据持久化切换记录恢复处理，不放任并发 apply |
| 恢复旧状态后新版会话不可见 | 作为可接受的历史取舍记录，不改写原绑定 |

## 5. 非功能需求

| 编号 | 类型 | 要求 |
|---|---|---|
| NFR-REL-01 | 绑定完整性 | 受保护记录逐条一致，任何身份变更都不能被静默接受 |
| NFR-REL-02 | 一次性成功保障 | 前置门禁全绿才切换；取证材料齐备；迁移不可逆，不提供回退 |
| NFR-REL-03 | 有界执行 | 快照、迁移、启动、校验和恢复有独立超时；HTTP 断开不导致半次切换 |
| NFR-REL-04 | 中断一致性 | 未完成操作可发现、不可并发覆盖；失败保留 error 终态，不假成功、不自动回退 |
| NFR-SEC-01 | 多用户隔离 | 会话、模型、文件、浏览器、平台凭据和工具上下文不能跨用户泄漏 |
| NFR-SEC-02 | 凭据保护 | 运行时注入；保护备份和配置权限；诊断脱敏 |
| NFR-COMPAT-01 | 版本兼容 | 固定目标版本/依赖与原镜像恢复组合，不 fork 上游 |
| NFR-COMPAT-02 | 产品兼容 | 原绑定、双 IM、现有 HTTP 契约、Agent 热重启和模型重启生效保留 |
| NFR-PERF-01 | 验证开销 | 绑定批量读取，路由批量核对，不为每个用户启动一个 CLI 或发网络请求 |
| NFR-PERF-02 | 容量边界 | 保留实际 `max_users` 与并发配置；不承诺 10→50 用户或未测性能提升 |

## 6. 范围与边界

### 6.1 范围内

稳定版本兼容升级；企微和 Mattermost；DB 绑定保护与原机器人复用；配置/SDK/重启适配；用户隔离与业务资产回归；升级材料取证、原位一次性切换、切换后验收及中断处理；工作量与后续收益说明。

### 6.2 范围外

- 绑定表结构改造、Console DB 数据迁移、重建用户/Agent、机器人换号。
- 微信业务启用及扫码登录态迁移。
- 以生产副本连接真实机器人进行演练、影子机器人或新旧机器人同时在线。
- OpenClaw 上游 fork、单用户单 Pod 架构迁移。
- 容量扩大到 50 用户、浏览器/SOP 服务拆分、CodeMode、技能自学习/Workshop、默认启用新记忆引擎。
- 前端页面重构、新的复杂运维门户、零停机承诺。
- 升级失败自动回退、跨 SQLite 迁移的降级恢复。
- 自动发送真实验收消息、生产构建与部署；需要后续明确实施授权。

### 6.3 前置假设与边界

生产 DB、主密钥和原 IM 凭据目前可用；运维可安排目标 Pod 维护窗口并取得状态离线副本（验证/取证）。不存在提前演练环境，不假设有多个生产 Pod。

可用性取决于实际通道连接与路由，不因 DB 完整就自动成立。存储环境、可用空间、目标版本及实际外部账号清单在实施前核对，不将它们伪装成已确认事实。

## 7. 依赖与风险

### 7.1 依赖

| 依赖 | 内容 | 确认时点 |
|---|---|---|
| 精确版本清单 | OpenClaw、双通道插件、Node、浏览器、自有插件及旧镜像 digest | 编码/发布基线确定前 |
| 状态存储能力 | 原卷静止复制/存储快照、外部工作区覆盖及空间 | 正式切换前 |
| 原数据库与主密钥 | 绑定读取、机器人配置解密及安全备份 | 正式切换前 |
| 原 IM 账号 | 企微 Bot ID、Mattermost 机器人用户身份 | 切换前采集与切换后核对 |
| 正式验收参与人 | 切换后真实消息、双用户隔离及业务技能验证 | 上线窗口确定时 |

### 7.2 风险

| 风险 ID | 风险 | 处理方向 |
|---|---|---|
| RISK-01 | SDK、插件配置或依赖不兼容 | 固定组合、静态与合成数据自动化检查，正式切换后校验 |
| RISK-02 | 新版存储改写不可逆，旧镜像不能读取新状态 | 前置门禁全绿后一次性成功；不设计回退，失败停 error 人工修复 |
| RISK-03 | DB 完整但新版路由语义改变 | 全量运行时解析；禁用默认路由兜底验收 |
| RISK-04 | 新默认扩大跨 Agent 权限 | 显式隔离配置与 Runtime Guard 回归 |
| RISK-05 | 新旧机器人同时连接 | 目标 Pod 串行停旧启新 |
| RISK-06 | 切换中配置变化或 Console 中断 | 操作排他、冻结相关写入口、持久化阶段与启动恢复 |
| RISK-07 | 取证材料不完整、磁盘不足 | 改写前核对材料与空间；失败停 error 保留材料，不自动回退 |
| RISK-08 | 历史处理误删技能、凭据或定时任务 | 历史与业务资产分别保护；自动兼容/自动新会话，原件保留，不手工删改 |
| RISK-09 | 错误日志泄漏凭据 | 全链路脱敏与权限测试 |
| RISK-10 | 无演练导致上线前无法证明真实 IM 可用 | 明确验证边界，正式切换后验收；不宣称已演练或零风险 |
| RISK-11 | 长任务恢复重复产生业务操作 | 切换前排空；不自动重放未知副作用任务 |
| RISK-12 | 大量路由核对引起资源竞争 | 批量读取与 RPC，避免每用户 CLI fan-out |
