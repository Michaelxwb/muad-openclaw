# mss-event-autoflow — NGES+MSS 自动化运营总调度

把「监控到客户有新事件 → 走完整分析 → 输出并发送推送文案」全流程串起来，是《NGES+MSS 的 Claw 自动化运营》流程 步骤1~10 的**总编排接入点**。

> ⚠️ 当前运行模式 = **人工确认（human-in-the-loop）**：整链在关键处置/推送给客户前需人工把关；流程整体验证成熟后可切换为自动跑。本 skill 只做"顺序调度 + 输入输出衔接 + 人工等待 + 取消"，**具体能力全部委托给子 skill**，不重复实现。

## 涉及的子 skill 与职责（阶段对齐）

| 阶段 | 子 skill | 职责 |
|---|---|---|
| 步骤1-4 | `monitor-security-events` | 事件监控：事件信息 + 资产业务信息（含NGES安装）落盘到事件文件夹 |
| 步骤5 | （人工） | 请求用户定位该事件的 **CGID**（当前网络不通，先人工关联；后续自动关联时替换此步）|
| 步骤6 | `mssp-rawlog-query` | 按 CGID 查询 ClickHouse，产出 GPTRawLog.json |
| 步骤7-10 | `gptrawlog-push` | 情报补充(ioc-context) + 分析 + 推送判定 + 生成推送文案 + 处置问询回填 |
| 随文案同轮截图 | `ti-redirect-analyze` | 判定推送且有 ioc-context 命中(有结果且恶意) IOC 时，与文案同轮对这批 IOC 生成 TI 情报截图，随文案一并返回 |
| 结束 | （本 skill） | 校验产物并把最终推送文案 + 情报截图发到企微会话 |

## 触发词

自动化运营/走完整流程/有新事件自动跑/监控到新事件帮我分析推送、NGES+MSS 自动。

## 运行模式（先人工，后自动）

- 当前：**human-in-the-loop**。每个新事件：
  1. 运行到「步骤5 求 CGID」时**暂停并询问用户**；
  2. 在**推送给企微会话客户前**做一次人工确认/展示最终文案。
- 成熟后启用 **auto 模式**（`--auto-cgid`：若 mssp 事件已带可自动解析的 CGID 则跳过人工；发送前仍可保留人工确认开关）。

## 强制阶段旅程（执行合同，顺序推进，不得跳步）

### 旅程 1 —— 确认触发范围（同 monitor-security-events 门禁）
开始任何平台/脚本调用前，明确获得：
1. 要监控的一个或多个客户。
2. 监控时长（正整数分钟）或起止时间。
缺项只询问缺项；不得用配置/记忆/默认补齐；门禁未过不得调客户/事件/资产接口。

### 旅程 2 —— 步骤1-4 事件监控（调 monitor-security-events）
- 确认客户（`resolve_customer.py` 解析 → 用户确认 company_id）。
- 运行事件监控，逐客户逐事件产出：**事件信息 + 资产信息落盘到本事件事件文件夹**。
- 若窗口内无新增事件 → 结束，输出"无新增事件"。

### 旅程 3 —— 步骤5 人工关联 CGID（关键人工点，带超时）
对每个需处理的**新增事件**（仅取推送候选，如 black/重点价值；是否为推送候选见后续判定，先按需询问）：
- 向用户（企微会话）发送询问：给出该事件的事件ID/名称/主机IP/关联告警，请其提供对应的 **NGES 事件 CGID**。
- **超时策略**：等待最长 **10 分钟**。若用户在 10 分钟内未给出 CGID → **取消该事件任务**，记录"被取消（超时未给CGID）"。

> 询问模板：
> ```
> 事件 {事件名}({事件ID}) 主机{IP} 属 {客户}。请提供该事件在 NGES 设备上对应告警的 CGID（当前为人工关联，后续自动）。若 10 分钟内未提供将取消该任务。
> ```

### 旅程 4 —— 步骤6 取 GPTRawLog（调 mssp-rawlog-query）
拿到 CGID 后，调用 `mssp-rawlog-query` 将该事件的 **GPTRawLog.json 落盘**到本事件文件夹（含 情报命中/行为树/分析 原始数据）。

### 旅程 5 —— 步骤7-10 分析+情报+判定+文案（调 gptrawlog-push）
- 以 GPTRawLog.json + 该事件资产信息为输入，运行 gptrawlog-push：情报补充(ioc-context) → 推送判定 → 处置问询（客户给实际处置动作）→ 生成/回填最终文案。
- 情报补充阶段：`ioc-context` 对 `threatList` 命中情报的实体查研判上下文；记录哪些 IOC 返回了有效恶意结论（这一步的“命中集”正是下一步 ti-redirect-analyze 触发对象）。

### 旅程 5.5 —— 推送后情报截图（调 ti-redirect-analyze，随文案同轮完成）

- 只要推送判定为「推送」且命中恶意 IOC，情报截图就在 gptrawlog-push 产出 `*_推送文案.md` 的同时一并生成（同一轮流程内完成），**不允许把截图留到用户二次单独催办**。
- 仅对“ioc-context 查询到有效结果且研判确认为恶意”的 IOC 逐一调用 `ti-redirect-analyze` 生成 TI 情报快照；未命中情报（0条/超时）或未查询的实体、人工判为误报/无关的实体：不调用、不截图。判定不推送或无一命中时不截图，并在收尾说明。
- 快照按 `ti-redirect-analyze` SKILL.md 截报告摘要区，写事件文件夹并登记到 `*_情报截图证据.md`；实现细节（判定/裁剪坐标等）以 gptrawlog-push §5.6 为准。

### 旅程 6 —— 人工确认后发送（文案 + 情报截图同轮一并）

- 将最终 `*_推送文案.md`（及其 `*_情报截图证据.md`/TI 快照）展示给用户做**校验**（这是推给客户前的人工把关点）——**文案与 TI 情报截图同轮一并展示/返回**，不得分批两次才凑齐。
- 确认后，**把文案发送到当前企微会话中的客户侧**；确有成图证据时，**同批**把 TI 情报截图作为附图一次性发给客户/归档（`MEDIA:<截图>`）。
- 已确认/超时的处置、客户端联系人均以该企微会话为准。

## 产物归档（每事件一个文件夹）

沿用 gptrawlog-push 约定：**每次分析的事件整文件夹作为一个目录，不同事件不同目录**。所有技能（本编排 + gptrawlog-push + 各处理子技能）共用**同一个统一事件归档根**：规范根 = `${SKILL_OUTPUT_DIR}/事件归档`（平台 per-user 可写区，谁调用归到谁行下，换账号自动隔离不错位）；无 guard 的本地调试回退到本技能工作区顶层 `事件归档/`（不做按 skill / 按 CGID / 按临时目录拆分）。

```
<统一事件归档根 事件归档>             ← 根解析同 gptrawlog-push resolve_archive_root()：
                                          显式 `-o`/EVENT_ARCHIVE_ROOT → ${SKILL_OUTPUT_DIR}/事件归档 → 本地工作区顶层 事件归档
└── {客户}_{时间戳}_{主机IP}_{事件名}/  ← 该事件全过程目录（永不删除/覆盖）
 ├── 事件信息.json / .md                      ← 旅程2 落盘：事件ID/名/主机IP/关联告警
 ├── *_资产信息.md                            ← 旅程2 落盘：资产业务信息（含NGES安装）
 ├── *.gptrawlog.json                         ← 旅程4 落盘：GPTRawLog（原始副本）
 ├── *_分析输入.md                            ← gptrawlog-push 解析产物
 ├── *_gptInput.json                          ← 行为数据原始输入
 ├── *_基础信息.json                          ← cgId/alertId/agentId
 ├── *_情报补充信息.md                        ← 情报额外信息（ioc-context 填充）
 ├── *_推送判定.md                            ← 判定（中间过程）
 ├── *_推送文案.md                            ← 最终推送文案（发送前需人工确认）
 ├── *_情报截图证据.md                        ← （推送定稿后）ti-redirect-analyze 对命中IOC的TI快照记录
 └── *_推送卡片.md                            ← （可扩展）归档卡片
```

- **多客户/单事件**：客户维度建子目录或按客户区分事件目录前缀，避免混淆。
- 新事件追加写入，历史事件文件夹原样保留；**禁止 rm/rmdir 清归档**。
- 每个事件目录中保留从"事件信息→资产→rawlog→分析→情报→判定→文案"的完整链路，任一环节可回溯。

## 子 skill 委托方式（不重复实现）

按阶段依次阅读并遵循对应子 skill 的 SKILL.md：
1. `monitor-security-events` → 旅程 2
2. `mssp-rawlog-query` → 旅程 4
3. `gptrawlog-push` → 旅程 5（情报补充让 `ioc-context`）
4. `ti-redirect-analyze` → 旅程 5.5（判定推送且有命中恶意 IOC 时，与文案同轮生成 TI 情报截图一并返回）
5. 子 skill 各自的登录态、凭据、命令、输出格式以其 SKILL.md 为准；本编排 skill 不重新请求平台凭据，只做衔接与人工步管理。

## 超时 / 取消 / 中断约定

- 步骤5 人工 CGID：等待 ≤ 10 分钟，超时**取消该事件任务**（不阻塞同一批其它事件）。
- 处置问询（gptrawlog-push 内）：默认等待客户端处置答复；超时策略按 gptrawlog-push 约定。
- 任一子调用脚本失败：如实上报，不伪造；单事件失败不拖垮整批，批量时逐事件标记成功/失败。

## 执行纪律

1. 严格按阶段顺序推进，不跳步、不合并不必要的步骤；每个衔接都要把上游产物路径显式传给下游。
2. 客户端信息、推送文案在前置人工确认通过前**不得发送**出企微会话。
3. 不泄露 ClickHouse 密码/cookie 等凭据；不伪造数据；找不到的字段用 `-`。
4. 每事件产物落盘到独立事件文件夹，保持可回溯，不删除过程文件。
5. 第 5 步当前强制人工，不自行猜 CGID；后续自动关联能力就绪后再改为可自动解析。
