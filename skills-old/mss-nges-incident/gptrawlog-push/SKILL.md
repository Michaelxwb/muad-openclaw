# gptrawlog-push

对终端GPT事件日志（GPTRawLog.json，含 analysePrompt 的行为数据与 analyseAnswer 的初步研判）进行解析分析，结合资产信息，并针对分析中命中情报的实体调用情报接口补充研判依据与遏制范围，最后综合生成对客户的推送文案。

## 用法

```
/gptrawlog-push <GPTRawLog.json>
/gptrawlog-push <GPTRawLog.json> --asset-name "财务部-张三-PC" --asset-ip 10.158.45.246
/gptrawlog-push <GPTRawLog.json> --done "已隔离样本0m2OF1Y81.exe;已封堵C2 47.243.29.7" # 人工已处置动作
/gptrawlog-push <GPTRawLog.json> --ioc 47.243.29.7 --ioc 5251b98614acffe5c856f4039ca03da3 # 手动指定调查实体
/gptrawlog-push <GPTRawLog.json> --no-push # 仅做分析判定，跳过文案
```

## 前置依赖

本 skill 自带或依赖以下脚本与相关能力：

- `scripts/parse_gptrawlog.py` — 解析 GPTRawLog，产出 `*_分析输入.md` / `*_gptInput.json` / `*_基础信息.json`（skill 已自带，调用：`python scripts/parse_gptrawlog.py ...`）。
- 资产信息 — 来自 MSSP/MSSW 平台（经覆盖监控 skill 步骤 3 的资产接口获得），写入 `*_资产信息.md`。
- 情报信息 — 调用 `ioc-context`（研判上下文）+ `ti-redirect-analyze`（TI 截图证据），写入 `*_情报补充信息.md`。

## 流程

### 1. 输入检查

确认两项输入是否就绪（缺一不可，否则先补齐再继续）：

- **GPTRawLog**（必须）：终端GPT事件日志
- **资产信息**（必须）：事件主机对应资产/业务信息，从 MSSP/MSSW 平台获取（资产名称、主机名称、业务名称、业务等级、资产类型、设备覆盖情况；**关键确认事件主机是否安装 NGES**）
  - 资产信息缺失时，需先经相应监控 skill 资产接口补齐 `*_资产信息.md`，再继续；没有资产信息不得臆造（字段缺失统一用 `-`）

### 2. 解析 GPTRawLog

```bash
python scripts/parse_gptrawlog.py <gptrawlog.json> -o 事件归档 --cgid <可选>
```

> 主机信息不从脚本命令行传入；由**前置步骤的资产信息文件**（如 `demo/10.12.1.234_资产信息`，主机 IP 见其文件名 `10.12.1.234` 或内容字段）提供，归档时按该资产信息归属到本 skill 事件目录下。

产出 `事件归档/{客户}_{时间戳}_{主机IP}_{事件名}/` 事件文件夹（统一归档根自动解析，见 resolve_archive_root），内含：
1. `*_分析输入.md` — 供后续分析的结构化摘要：事件名称、GPT研判标签、定性标签、analyseAnswer 全文、gptResponse 结构化研判（analysis 的 title/explain/evidence）、威胁情报 IOC 汇总、恶意实体（根因/入口）、终端GPT处置建议、进程树概览
2. `*_gptInput.json` — 完整 threatList / treeList / virtualEdges（行为数据原始输入）
3. `*_基础信息.json` — cgId / alertId / agentId 等

**重点关注字段：**
- `analysePrompt` 中的 `threatList`（情报命中）、`treeList`（进程行为树）、`virtualEdges`（跨树行为关系）——三者构成完整行为输入
- `analyseAnswer`：标签（black/gray/white）、攻击过程分析、定性标签、事件总结、入口信息（入口名/动作/根因实体）、处置建议
- `taskContent.gptResponse`：结构化研判 analysis、恶意实体（hashTi/ipTi）、disposeSuggestion

### 3. 调用情报接口补充情报

**仅针对解析结果 `threatList` 中命中情报的实体**调用情报接口；行为树中出现但未命中情报的其他实体（事件其他实体段）默认不调用。如需调查，用户可手动指定任意实体（`--ioc` 参数）。

- `ioc-context`：输入 IOC，返回研判上下文（【研判结论】【研判依据】【影响评估】）
- `ti-redirect-analyze`：输入 IOC，返回 TI 截图证据

### 4. 推送判定

**不推送的场景（命中即停，输出不推送说明）：**
- 业务：资产/事件属于业务行为（如企业合规预装、测试验证），写明业务名与依据
- 低危：gray 标签、低危 PUP/广告软件、无完整攻击链的可疑行为
- 误报/无威胁：white 标签，敏感行为有合理解释；未建立连接且无关联事件的单次恶意域名访问

**推送的场景（全部满足）：**
- black 标签，且存在真实攻击特征之一：恶意文件落地并执行（情报判定恶意程序）、木马/远控/间谍行为（C2外联、持久化、注入等）、攻击链完整（投递→执行→持久化→C2）

输出 `*_推送判定.md`：
```markdown
# 推送判定
- 事件：{事件名称} | 主机：{IP}（{资产名}） | 标签：{black/gray/white}
- 判定：推送 / 不推送（原因：业务 / 低价值 / 误报 / 无真实攻击）
- 判定依据：逐条列出（情报命中、攻击链、业务归属等）
- 情报补充结论摘要（命中实体的研判结论）
- 下一步：{生成推送文案 / 归档观察 / 无需动作}
```

### 5. 生成推送文案

以 `*_分析输入.md` + `*_情报补充信息.md` + `*_资产信息.md` 为输入，生成推送文案 `*_推送文案.md`。

**文案结构（两段式推送：先一段“凝练版”置顶，再一段“标准详版”默认不变）**

> 每次推送 = **两段**。第一段凝练话术放在最前（供客户一眼抓住要害），第二段为现有标准文案（保持既有格式不变）。具体见 §5.1 新增约束 A/B/C 详细说明。

**标准详版模板（= 现有文案默认不变，作为第二段）：**

```
【深信服 安全事件通告】已遏制，未对系统造成实际危害   ← 或“已遏制，存在残留待处置”（见“业务危害前置+已遏制”约束）
事件名称：{事件名（如“设备存在通过xx投递…的钓鱼攻击，同时发现恶意文件”）}
事件类型：{事件类型（木马/钓鱼/广告软件/恶意程序/远控等）}
事件ID：{E…}
影响业务：{IP(资产名/主机名)，如 10.88.48.138(Ren)}
资产信息：{资产类型+资产名（含用户 人名/账号，如 个人PC Ren（用户 刘仁杰））}
组件检出时间：{首次发现，YYYY-MM-DD HH:MM:SS}
业务危害：{一句话消解句，如“木马已被 NGES 实时拦截，未对您的系统造成实际危害”}
处理时效：{整个事件已于 N 分钟内闭环（处置完成时间 − 首次发现时间；仅真实闭环/遏制时不写“闭环”，改为“已遏制”）}
（空行）
尊敬的xx老师，{发现时间}，发现{资产类型} {业务/资产名}（{IP},账号{账号}）{一句话事件概要}，{既成处置+消解句}：已被XX拦截/查杀/隔离，并未对您的系统造成危害 / 仍在持续告警需关注，详情如下：

【事件概述】{编号时间线列表：每条=时间点+该时刻行为；收束为当前处置/危害状态}

【事件研判】{先定性一句 + 两条证据链：静态特征分析（签名滥用/白加黑/随机路径/伪装名）→ 已执行行为证据（计划任务持久化/加白/删卷影/禁更新/外联C2等，逐条给实体与指令）；再单列一段如实、结合业务的危害陈述（不夸大不隐瞒）}

【事件遏制&处置】
深信服MSS已完成：
{1. 威胁实体遏制：[已遏制] C2/IOC/恶意域名封堵+黑名单/情报监测同步，可联动识别同源变种}
{2. 全网排查：[已处置] 关联资产排查结论/批量拦截（若情报或事件可枚举关联威胁实体/同源变体时写，列明已加入黑名单/拦截的实体清单）}
需要老师处置内容：
{1. 仅客户必须动手的最小项 [待处置]，≤2~3 条}
```

> **通告抬头块（本 skill 生成文案时置顶必带，结果前置）**：gptrawlog-push 生成的 `*_推送文案.md` 在正文之上**置顶** `【深信服 安全事件通告】…` 块。字段值取平台事件/告警/事件名与事件类型、事件ID、检出时间，及前置资产业务信息；**影响业务**如平台未给，按 `{IP}({资产/主机名})` 拼；缺值用 `-`，不明事件类型据定性写，**不臆造**。

**人工处置确认**：人工已完成处置动作经对话/`--done` 提供后回填到「深信服MSS已完成」或「需要老师处置」；未提供 MSS 侧动作时不停留在占位——先列出已明确自动处置（如 NGES 隔离/封堵）为已遏制项，其余必办项进「需要老师处置」，并向客户发处置问询（见 §5.5）。

### 5.1 新增约束（两段式推送 · 业务危害前置·已遏制 · SLA 时效）

> 本节三条约束为本次新增，与既有 §文案硬性要求并用，不得冲突时丢项；标准详版（第二段）保持既有格式不变，新增只影响抬头结果前置字段、SLA 时效字段，以及在第一段新增一段凝练话术。

**约束 B：业务危害前置 + “已遏制”结果抬到头上（结果优先）**
针对推送，先把结果放在抬头、把最重要的信息放在最前，给客户的阅读心理排序应是：**事情大不大 → 要不要紧急做动作 → 发生了什么**。
- 抬头标题直接带结果：在 `【深信服 安全事件通告】` 之后紧跟标定处置结果，示例：
  - 已彻底拦住 → `【深信服 安全事件通告】已遏制，未对系统造成实际危害`
  - 已按住但还留有尾巴需客户动手/还有残留 → `【深信服 安全事件通告】已遏制，存在残留待处置`
  - 仍活跃未按住 → 不得写“已遏制”，如实写状态（如“检出并在处置中，请尽快配合”）
- 将“影响业务/资产（谁中招）+ 严重程度 + 一句危害结论”在抬头块内的「业务危害」字段前置体现，`业务危害`字段放在事件 ID / 影响业务之后，客户先看到“与我业务相关、要不要动”，再进入发生了什么。严重程度词（高危/中危/低危）按事件定性/情报等级如实标（如`【高危·已遏制】`），未定级不准臆造。

**约束 C：SLA 时效性体现（快处置，体现响应快）**
用“处置完成时间 − 首次发现时间”算出闭环耗时，在抬头块内**业务危害之后**加一条  `处理时效`（或 `MSS响应时长`）字段，用一句话话术告诉客户“我们在很快的时间就处理完”，例如：`处理时效：整个事件已于 10 分钟内闭环`。
- **计时口径**：起始=事件/样本“首次发现时间”（组件检出时间，即抬头 `组件检出时间`）；结束=处置/闭环完成时间（以人工或平台确认为准）。处置完成时间缺失时，可近似取「捕获到已遏制动作的时间/告警处置完成时间」，但**不得虚报精确闭环分钟数**；若无法核定结束时间，如实写“检出后已即时隔离，处置常态 0 分钟级响应”等不带精确数字的表达。
- 仅在事件确已闭环/已遏制时写“闭环”或“已遏制”；仍未处置完毕则写“处置中，已用时 N 分钟，MSS 正持续跟进”，不得虚报闭环。

**约束 A / 结构化输出：两段式推送（第二段=现有文案默认不变；在其前新增一段高度凝练话术）**
在现有标准文案（详版）之上，先生成**一段高度凝练的推送话术**，让客户一眼看出：攻击是真的、已被按住、没扩散、影响和下一步清清楚楚。两段顺序固定：第一段凝练版 → 第二段现有详版（默认不变）。

凝练版（第一段）句式（一段到底，直接给信息）：`【严重程度·已遏制】{资产定位}发现{攻击定性·用业务语言}，已{按住方式}，未造成/是否扩散+影响。处理详情：已{MSS已完成动作}；建议/下一步{客户最小项}。`

示例（银狐木马）：
```
【高危·已遏制】核心资产 个人PC DESKTOP-4LOACFG 发现银狐木马执行，已自动阻断外联，未造成进一步危害。处理详情：已封禁恶意IP 2个、域名1个，终止恶意进程；建议隔离终端并清除恶意计划任务。
```

凝练版硬性要求：
1. 首词即严重程度+已遏制结论（业务定性词准确，承接约束 B）；
2. 明确主体（哪台资产/哪个业务被波及）+一句“攻击是真的”（用研判结论的一句话，不带内部黑话）；
3. “已被按住”：写明按住方式（自动阻断外联/终止进程/封禁 IOC/隔离样本，结合处置详情）；
4. “没扩散”：给影响面判定（单机/是否全网扩散），能枚举的列已封禁个数；
5. “影响+下一步”收在句尾：本事件影响一句话 + 需要老师做的最小下一步项（承接处置两栏）；
6. 一句话一段，面向客户可扫读，不堆技术名词罗列；整段为一个代码块/文本，紧随其后换行输出详版（第二段）。

两段均在同一 `*_推送文案.md` 内，第一段在上方；对外发送时两段先后一并发出，详情=第二段详版。

**待处置/兜底动作归属规则**（结合情报遏制范围，先分类再归位）：
- **威胁实体遏制**（C2 IP/域名/URL/恶意 hash）：防火墙/端点封堵、加 NGES 黑名单 → **归「深信服MSS已完成」**（情报【影响评估】说明可放心阻断的才写）；
- **关联资产全网排查**：若情报/事件显示多主机同源或可枚举关联威胁实体 → **由 MSS 执行全网排查并将结论写进「深信服MSS已完成」**（如“已对全网排查，未发现/发现 N 台主机命中”）;
- **隔离/查杀**（恶意文件已由 NGES 自动隔离）：归「深信服MSS已完成」[已遏制]（如“已隔离但可能复发”则把根除/清理移到客户必办项）;
- **客户必办且必要项**（终归「需要老师处置」，≤2~3 条）：删除恶意目录/原始投放文件、移除持久化项（计划任务/服务/启动项/Run键/Defender 排除项/禁用的更新服务，如确需手工整修）、必要时账号密码重置、入口溯源宣导;
- **默认不推客户的兜底/服务方动作**：全盘扫描、病毒库入库、持久化主动自查、扩展排查等——除非确需客户配合，默认由 MSS 侧执行或作为“可提供协助”，不当作客户待办堆积；
- 入口/除根未溯源到的 → 写“建议排查下载记录/IM 渠道/同网段”，不写死结论。

**文案硬性要求：**
A. **(5条规范项) 结构定式（不可省、不可乱序）**：
   1. **通告抬头必带且结果前置已含危害**：置顶【深信服 安全事件通告】块，标题紧跟“已遏制…”结果（如`已遏制，未对系统造成实际危害`/`已遏制，存在残留待处置`）；抬头主干字段的**末两项依次为「业务危害」「处理时效」**——业务危害用一句业务可读的话简洁说清现状/消解结论（如“恶意文件已被 NGES 实时拦截，未对您的系统造成实际危害”），处理时效给闭环耗时（如“整个事件已于 10 分钟内闭环”）；不堆技术细节。
   2. **事件概述 = 关键时间线，只讲与攻击直接相关的关键时刻+行为**：编号列表，每条=时间点+该时刻的关键动作；跳过/合并与攻击无关的铺垫（接收文件等如非必要不展开系统内幕），末句落到当前处置/危害状态，全段精炼不长篇。
   3. **事件研判分两段证据：静态特征分析 + 动态（已执行）行为**：先一句定性（客户可懂的自然语言），再 `静态特征分析：`（签名滥用/白加黑/随机路径/文件名伪装等；**无静态特征证据就不写该段，不写空标题**），再 `动态行为（木马在主机上已执行）：`（持久化/加白/删卷影/禁更新/外联C2等逐条给实体与指令）。
   4. **无编号技术黑话**：面向客户正文不出现"black/gray TAG"等内部标签与系统内幕进程叙事，改用客户能懂的语言，家族名最多作括号佐证。
   5. **遏制&处置分两栏且客户栏极简**：`深信服MSS已完成：`（威胁实体遏制/全网排查，已封堵/已隔离项打 [已遏制]/[已处置]）与 `需要老师处置内容：`。**需要老师处置只列最精的、易上手的关键动作，≤2~3 条**；全盘扫描/病毒库入库/批量排查等兜底类由 MSS 或作为协助承担，不推给客户当待办堆叠，避免繁琐低效操作。
0. **去冗余·一文一义**：通告抬头块已承载事件名/类型/IP/危害结论等关键信息，正文各板块不重复复述抬头已列字段，也不在板块间重复同一结论。开场定式句（尊敬的…）与【事件概述】第1条讲的是同一句概要、【事件概述】落点与【事件研判】危害段会出现同一句"已被拦截/未造成危害"——原则是同义结论只出现一次、后出现的位置必须叠加**新证据或新维度**才保留，纯重复一律删。洁净的单事件文案可直接从通告块切入编号概述+研判，语句密度高、少打扰（详见§去冗余裁切清单）。
1. **专业听得懂**：技术细节保留（路径/任务名/端口/MD5/时间/账号），但用一句业务语言解释"对客户意味着什么"；术语首次出现给通俗说明（如"持久化=开机自启，删除不彻底极易复发"）。
2. **开篇给业务定心/状态**：开场紧承概要后第一句即用业务可读表述讲清"现在到底怎样、对我的业务有无影响"（如图标"该恶意程序/外联已被 NGES 拦截/查杀，并未对您/系统造成危害"，或尚未拦截则如实写"正持续关注需配合处置"），不只堆技术动作。
3. **危害如实、结合业务讲清（不夸大不隐瞒）**：确需描述危害时，在【事件研判】末尾单列一段，按客户所属业务关联具体可感知影响（如该样本会窃取浏览器 Cookie/账号、拖走涉发票报销/财务数据、或可被远程控制/横向扩散），基于情报与攻击链事实陈述；**不夸大不隐瞒**——有实据的后果写明，无实据的不可危言定性（不写"业务严重瘫痪/必然数据泄露"式臆断），也不因已拦截而过早断言"绝对无影响"。
3. **响应体现专业与省心**：突出"已检出→已拦截/隔离→已在全网排查→持续监测"，让客户感受到响应快、免打扰；只给最精客户必办项与可提供协助。
4. **给证据**：时间点、实体名、MD5、C2、路径、账号写全，支持客户拉群向业务部门复述。
5. **分点叙述**：建议 1、2、3 分点，避免小作文式长段落（概述/研判用编号列表更清晰）；全文避免浮夸形容词（"严重威胁"可改为具体后果）。
6. **多主机/复发事件**：开头一句总览（N台主机共N起，与之前事件同源/复发），单事件已处置动作在相应事件下标注。
7. **不承诺、不写死**：没有溯源到的入口写"建议排查"，不虚构下载来源；处置状态以人工/平台确认为准。
8. **不堆内部技术标签与系统内幕**：面向客户的正文不抛内部标签/黑话（如"black/gray TAG"、"Riskware 家族"、"Agent.uyyg" 家族代号当结论），也不罗列系统内部进程叙事（谁用 dllhost/svchost 拉起、签名内幕、"主机已装 NGES 属重点防护"等系统声明）；改用客户可懂的自然语言描述（"威胁情报已标记该程序为恶意木马"、可提"伪装打印工具诱导运行"），家族名最多作括号佐证，不让内部定性/系统实现做结论句。

**【遏制&处置板块·克制原则】**：面向客户少打扰、明确责任主体——
- 强约束分两栏输出：`深信服MSS已完成：` 与 `需要老师处置内容：`。MSS 栏在本 skill 生成文案时按**两条带标题子项**展开：`1. 威胁实体遏制：`（[已遏制] 封堵 C2/恶意域名/IOC + 黑名单、情报监测同步、可联动识别同源变体）与 `2. 全网排查：`（[已处置] 关联资产排查/批量拦截，可枚举时列已拦截实体清单）。若某子类本事件无实据（如仅单机无全网排查必要），省略该子项，不写空标题。`需要老师处置内容：`仅含客户必须动手的最小项，[待处置]，通常 ≤2~3 条。
- 兜底/服务方类动作（全盘扫描、病毒库入库、持久化主动自查、账号批量排查等）不默认推给客户；确需客户配合才进“需要老师处置”。
- 不写泛泛之谈（"全盘查杀""定期加固""建议加强防范"）与明显重复项；同类收敛为一条。
- 已隔离/已清除/已封堵/已全网排查的项标[已处置]/[已遏制]并归入 MSS 栏。
- “还能提供什么协助”（上机根除/二次核查）放收尾一句，不当作待办堆叠。

**低价值场景的默认文案**：若判定为"不推送"但需要告知客户（如广告组件），输出轻量说明（一句话事实 + 无危害结论 + 观察建议），不按上述板块展开。

### 5.5 处置问询（独立步骤，主动向客户获取实际处置动作）

初版文案按「深信服MSS已完成 / 需要老师处置」两栏组织后，**skill 必须主动向客户发一次处置问询**，确认实际已完成的处理并回填，不能停留在未定稿状态。问询目的是：确认 MSS 侧主动处置（封堵/全网排查）是否有遗漏、并明确客户需动手的最小项。

**默认问询话术模板**（可直接发送）：

```
关于本次事件，MSS 已完成：{封堵 C2/IOC、恶意文件隔离等；全网排查结果}。
若属实，现需确认您侧是否已完成或将处理以下项，以便同步处置状态：
 ① 上机清理（删除 {恶意目录/文件/原始投递文件清单}）
 ② 移除持久化（删除计划任务 {名称}、移除 Defender 排除项等，如确需我方远程协助整修请告知）
 ③ （如有）重置受影响账号密码并核实异常登录
 ④ （如有）定位入口来源（下载记录/IM/邮件）并剔除隐患
以上均未做、需我方远程协助处置根除，也请直接告知。
```

**执行约定：**
- 问询必须在推送给客户前（或同步）发出；以客户/服务经理反馈处置动作＝唯一事实来源回填两栏。
- 客户未答复前，MSS 主动处置已知晓（NGES 自动隔离/C2 封堵）可先列为已遏制项，不臆造未证实动作；确需客户动手项保留[待处置]。
- 收到答复后：把已确认项移至对应栏，剩余保留，更新 `*_推送文案.md`（必要时同步 `*_推送判定.md`）。

### 5.6 情报截图证据（ti-redirect-analyze）—— 随推送文案一体返回（必做，非可选项）

**触发时机（必做）**：只要判定为「推送」且事件存在命中 ioc-context 且确认恶意的 IOC，情报截图就与 `*_推送文案.md` **在同一轮流程内生成并一同返回给用户**——不允许把截图留到用户再次单独提出要求才补做。推送文案生成/定稿后（含处置回填后的终版）立即执行本步；截图作为追加证据随最终推送一起归档/发送。

**随文案一体返回要求**：本轮最终回复必须同时包含——①推送文案（代码块原样输出）；②命中 IOC 的每张 TI 截图（用 `MEDIA:<截图路径>` 逐行附上）；③`*_情报截图证据.md` 的关键字段摘要。三者缺一即视为本次推送交付不完整，需在撤回前补齐。若判定为「不推送」或无一 IOC 命中（0条/超时/误报），则不截图，并在回复的收尾一句说明“无命中情报可截图”，不得因此把文案与截图拆成两轮追问。

触发对象（硬性门禁）：**只对 `ioc-context` 本事件中查询到结果、且研判结论确认为恶意的 IOC 调用 `ti-redirect-analyze`**。即以步骤3中 `ioc-context` 返回了有效【研判结论/研判依据】的实体为准，对这些命中实体的 IOC 逐个生成 TI 分析页快照。

不得对以下实体调用：
- `ioc-context` 无结果/未命中（0条/超时/接口未返回结论）的实体——跳过，不留空图；
- 仅出现在行为树、未命中威胁情报的“事件其他实体”（步骤3已约定默认不查情报）；
- 已被人工判为误报/无关的实体（如无关的 Edge 自启动项等系统常规项）。

若有 N 个实体命中，则为每个命中实体各生成一张截图；无一命中则不调 ti-redirect-analyze、不产出截图。

**执行方式（按 `ti-redirect-analyze` SKILL.md）**：
1. 判 IOC 类型（domain/url/ip/md5）；`flclashcn.com` → domain。
2. 运行 `python scripts/run.py --type <type> --ioc <ioc>` 得到重定向 URL。
3. 用 browser 打开该 URL，等待 SPA 渲染约 8s，确认落到 `analysis-platform/*_report/<b64>` 报表页。
4. 窗口宽 1400、fullPage 截图；按子 skill 给出的分型裁剪坐标截报告摘要区（domain/url/ip vs md5 不同），确保图中含标题 + SANGFOR标签 + 威胁等级/时间 等要点；布局偏移时按摘要元素 getBoundingClientRect() 重取坐标。
5. 裁剪图写入事件文件夹并保留原始截图副本（证据不删）。

**产物落盘**：事件文件夹内新增 `*_情报截图证据.md`，记录“本次命中且已截图的 IOC 列表 + 每张截图路径 + TI 关键字段（标签/等级/信誉/危害描述）”，供解读与追证。截图正文不插入长图片 URL 清单。**落盘路径与文案同在一事件文件夹，便于整文件夹随文案一起发送/归档。**

> 若平台页面未登录仍可见报告摘要，直接截图即可；TIP：同一批事件多个命中 IOC 依次截图，不在循环里高频重开页面。

### 6. （可扩展）事件归档卡片 + 收尾

将推送文案浓缩为 `*_推送卡片.md`：事件名、时间、主机、定性、关键IOC、处置状态、证据清单（截图/MD5/C2/时间点），便于后续与文案一起推送、客户归档或拉群转发。全部产物（原始日志、中间过程、推送材料）保留在事件文件夹中，**不删除**；输出结果摘要：事件文件夹路径、判定结论、待人工确认项。

**最终交付（收尾）**：本 skill 一次轮次即产出并向用户返回**完整推送交付包**——①`*_推送文案.md`（代码块原样输出）；②若判定推送且有命中恶意的 IOC，附图逐张 `MEDIA:<TI截图路径>`；③命中 IOC 关键 TI 字段摘要。文案与截图**同一轮一并返回**，不得把截图留到用户二次单独催办补做。收尾文本极简：事件文件夹路径 + 判定结论 + 待人工确认项 + 已附 N 张情报截图。

## 高价值推送文案规范总结（结合两版成品校准）

- **两段式推送（本次更新）**：每次对外推送先发**一段高度凝练话术**（首词=严重程度+已遏制结论，让客户一眼看出“攻击是真的、已被按住、没扩散、影响/下一步清楚”），再紧跟**现有标准详版**（第二段保持不变）。凝练版句式见 §5.1 约束 A 及下方示例。

- **通告抬头块（置顶，结果前置 + 已遏制标在标题；主干末段依次为业务危害+处理时效）**：标题 `【深信服 安全事件通告】{已遏制结论}`（如 `已遏制，未对系统造成实际危害` / `已遏制，存在残留待处置`）；主体字段：事件名称/事件类型/事件ID/影响业务/资产信息/组件检出时间/**业务危害**/**处理时效**；取平台事件+告警名与检出时间、资产业务信息、账号人名，**业务危害=一句简洁业务消解句**（如“该木马已被 NGES 实时拦截，未对您的系统造成实际危害”）；**处理时效=（处置完成时间−首次发现时间），如“整个事件已于 10 分钟内闭环”**（未闭环写“处置中，已用时 N 分钟”）。阅读排序：结果（大不大/已拦）→ 要不要动 → 发生了什么。字段不臆造，缺值用 `-`。

- **开场定式**：时间 → 发现{资产类型} {业务/资产名}（{IP},账号{账号}）{一句话概要} → {既成处置+消解句}（"已被…拦截/查杀,未对您造成危害" 或 "正持续告警需关注"）。需含业务信息（个人PC/服务器、是否核心、账号）。此句与通告块同义时不重复，见去冗余清单。

- **事件概述 = 只含攻击关键点的时间线编号列表**：每条=时间点+与攻击直接相关的那一时点关键行为（投递落地→样本执行→恶意行为→外联C2→检出拦截），**只讲与攻击相关的关键时间与行为**，跳过/精简无关铺垫（不用系统内幕叙述每一步）；末条给当前处置/危害状态。

- **事件研判 = 定性一句 + （可选静态段）+ 动态行为段（两段式证据链）**：先一句客户可懂定性；`静态特征分析：`（签名滥用/白加黑/随机路径/文件名伪装等，**无静态证据则不写该段、不写空标题**）；再 `动态行为（木马在主机上已执行）：`（持久化/加白/删卷影/禁更新/外联 C2 等逐条给实体与指令）；末尾按业务如实讲清危害（不夸大不隐瞒）。面向客户不使用 black/gray 等内部标签作结论。

- **遏制&处置两栏**：`深信服MSS已完成：` 栏内**分两条子项呈现**—— `1. 威胁实体遏制：[已遏制]`（C2/恶意域名/IOC 封堵+黑名单、情报监测同步、可联动识别同源变种）与 `2. 全网排查：[已处置]`（关联资产/批量拦截结论，可枚举时列明已加黑名单/拦截的实体清单）；随后 `需要老师处置内容：`（**仅列最精、易上手的客户关键动作 ≤2~3 条**，[待处置]，不明户繁琐低效项）；兜底/扫描/病毒库不默认推客户；协助一句收尾。两子项均有实据才写，只发生其中一类就写那一类、缺的省略不写空标题。
- **禁用**：无证据的定性（未溯源到入口就写"从xx下载"）；模糊处置（"已处理"无具体动作）；内部标签当结论句；系统内幕进程叙事；需求外低效繁琐操作堆积；夸大/隐瞒危害。

**§去冗余裁切清单（净化[通告块之下]正文；单事件适用）**：
- 通告抬头块已含"影响业务/资产类型+IP/危害结论"→ 开场定式的"尊敬的…{资产类型}{业务/资产名}({IP})"概要句，若与抬头重复且【事件概述】第1条已续写动作，则该长导入段可整段砍掉，通告块直接接编号概述；确保留开场时，压成一句时间+事件+消解，不复述抬头字段。
- 【事件概述】做"发生了什么"的客观事实时间线（时间+动作），【事件研判】做"为何恶意+何危害"的判定——两板块职责不重叠；概述末句的"已被拦截，未受影响"结论，研判危害段若再给同义句，则二选一，保留在研判危害/处置段更合理。
- 危害说明不必自成一段时并入攻击意图点后，但被合并段须同主题、且阅读转折完整；若并入造成一段多义，宁独立成段，不因拼行而牺牲可读。
- 收尾"可提供协助"与"需要老师处置[待处置]"不冗余：客户已能自行动手的最小项留待处置；如需 MSS 上机/复查才写收尾协助一句，非强推。
